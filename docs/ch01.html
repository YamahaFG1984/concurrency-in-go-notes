第 1 章

并发编程导论

「并发」这个词，不同的人理解不一样。这一章先给它一个实用的定义， 然后回答两个问题：为什么现代软件绕不开并发？为什么并发代码这么难写对？ 我们会认识并发世界里的「五大恶人」—— 竞态、原子性破坏、死锁、活锁和饥饿。

本章目标

  • 理解摩尔定律放缓、阿姆达尔定律和云计算如何把并发推到每个程序员面前
  • 分清「竞态条件」和「数据竞争」，知道为什么 time.Sleep 不是解药
  • 理解原子性取决于「上下文」，以及 i++ 为什么不是原子的
  • 认识临界区、死锁的四个科夫曼条件、活锁与饥饿
  • 学会用注释和函数签名把「并发约定」告诉调用者

先给「并发」下个定义

你可能还听过「异步」「并行」「多线程」这些词。有人把它们混着用，有人分得很细。第 2 章会专门讨论并发的哲学， 这里先用一个够用的定义：

★ 实用定义

当我们说两件事「并发」时，指的是它们在同一段时间里都在推进。你正在读这句话，世界上其他人也在各自生活 —— 你们是「并发」的。

并发是计算机科学里一个很大的话题，从理论建模、正确性证明到工程实践都有。本书只关注实际问题： Go 怎样为并发建模、这个模型会带来什么问题、以及怎样组合 Go 的原语来解决问题。

摩尔定律、Web 规模，以及我们面临的困境

1965 年，戈登·摩尔预测集成电路上的元件数每年翻一番（1975 年修正为每两年）。这个预测大体上一直成立到 2012 年前后。 当单核性能越来越难提升，芯片厂商转向了另一条路：多核处理器。

多核看起来绕开了摩尔定律的瓶颈，但很快大家撞上了另一条定律 —— 阿姆达尔定律（Amdahl's law）： 并行化能带来的提升，受限于程序中必须顺序执行的那一部分。

书里举了两个极端的例子：

  • 图形界面程序：用户点按钮、程序做事。整个流程被一个巨大的顺序部分卡住 —— 人的操作速度。给它再多核也没用。
  • 计算圆周率的各位数字：借助「龙头算法（spigot algorithm）」，这个问题可以被切成互不相干的小块， 属于「易并行」（embarrassingly parallel）问题。核越多越快，新的难题变成怎样合并和存储结果。

对于易并行的问题，推荐把程序写成可以水平扩展的：多开几个实例、多用几台机器，系统就变快。 2000 年代兴起的云计算让水平扩展变得廉价，也催生了「Web 规模（web scale）」软件 —— 通过增加实例来应对几十万并发请求，支持滚动升级、弹性伸缩和异地部署。

但代价是复杂度。2005 年 Herb Sutter 写了一篇著名文章《免费的午餐结束了》（The free lunch is over）， 他说：「我们迫切需要一种比现有语言更高层次的并发编程模型。」要理解他为什么用这么重的语气，就得看看并发到底难在哪。

为什么并发很难？

并发代码出了名地难写对。常常要改好几轮才能按预期工作，甚至上线几年后，因为磁盘变忙、用户变多这样的时序变化， 一个潜伏已久的 bug 才突然冒出来。好消息是：大家踩的坑都差不多，计算机科学家已经给它们起好了名字。

竞态条件（Race Condition）

竞态条件：两个或多个操作必须按正确的顺序执行，但程序没有写成能保证这个顺序。 它最常见的表现形式是数据竞争（data race）：一个并发操作在读某个变量，而另一个并发操作在不确定的时刻写同一个变量。 

var data int
go func() { // 用 go 关键字启动一个 goroutine，和下面的代码并发执行
	data++     // 第 3 行：写
}()
if data == 0 { // 第 5 行：读
	fmt.Printf("the value is %v.\n", data) // 第 6 行：再读
}

✓ 「一小时」思想实验

想象两个操作之间过去了一个小时：goroutine 被创建后过了一小时才开始跑；或者 goroutine 跑完后过了一小时程序才走到 if。 程序其余部分会怎么表现？对计算机来说时间尺度不同，但相对的时间差是一样的。

有人会想：那我在中间睡一会儿，等 goroutine 跑完不就行了？

var data int
go func() { data++ }()
time.Sleep(1 * time.Second) // 这是坏主意！
if data == 0 {
	fmt.Printf("the value is %v.\n", data)
}

数据竞争解决了吗？没有。三种结果依然都可能出现，只是越来越不可能。睡得越久，程序越「接近」正确， 但这个概率只会无限逼近、永远达不到逻辑上的正确。而且我们白白让程序多等了一秒。

★ 永远追求逻辑正确

在代码里加 sleep 调试并发问题可以，但它不是解决方案。竞态条件是最阴险的一类 bug： 它们可能在生产环境潜伏好几年，直到某次环境变化让「几乎总是按顺序执行」变成「这次没按顺序」。

Go 自带竞态检测器：go run -race main.go 或 go test -race ./...。 对上面的程序，它会直接报告 WARNING: DATA RACE 并指出读写双方的代码位置（详见附录 A）。 另外，Go 1.19 正式修订了内存模型：没有数据竞争的程序表现得「像顺序一致的」； 一旦有数据竞争，对字符串、切片、接口这类多字长的值，读到「撕裂」的半新半旧值甚至导致崩溃都是可能的。 所以数据竞争不是「结果可能有点不准」，而是真正的 bug。

原子性（Atomicity）

一个操作是原子的，意思是在它所处的上下文里，它不可分割、不可中断： 要么完整地发生，要么没发生，期间这个上下文里不会有别的事插进来。

关键词是「上下文」。在进程内是原子的操作，在操作系统层面不一定是；在操作系统层面是原子的，在整台机器层面不一定是。 所以讨论原子性时，第一件事是先说清楚「在哪个范围内原子」。

🔎 趣闻：游戏外挂与「原子性的上下文」

2006 年，暴雪起诉 MDY 公司的外挂程序 Glider（可以自动玩《魔兽世界》），获赔 600 万美元。 游戏的反作弊程序 Warden 会扫描内存寻找外挂，它把「扫描内存」当成一个原子操作。 但 Glider 利用硬件中断，在扫描开始前把自己藏了起来 —— Warden 的扫描在进程的上下文里是原子的，在操作系统的上下文里却不是。

每一步单独看是原子的，但原子操作组合起来，并不一定还是原子的。 如果上下文是「没有任何并发的程序」，那 i++ 在这个上下文里是原子的； 如果 i 只在一个 goroutine 内部使用、不暴露给别人，那它也是原子的。

为什么关心原子性？因为原子的东西在并发环境里天然是安全的。大多数语句、函数、程序都不是原子的， 所以我们需要各种技术来「强制」原子性 —— 难点在于判断代码的哪些部分需要原子、粒度多大。

🆕 新版 Go：带类型的原子变量 Go 1.19+

书中（第 1 章的活锁例子）用的是 atomic.AddInt32(&x, 1) 这种函数式 API，很容易忘记某处直接读写了 x。 Go 1.19 起推荐用 atomic.Int32、atomic.Int64、atomic.Bool、atomic.Pointer[T] 等类型， 它们只能通过方法访问，从类型上杜绝了「漏掉原子操作」： 

var hits atomic.Int64   // 零值即可用
hits.Add(1)             // 原子 +1
n := hits.Load()        // 原子读取

内存访问同步

回到数据竞争的例子，加一个 else，让程序无论如何都有输出。程序中需要独占访问共享资源的部分叫临界区（critical section）。 这个例子有三个临界区：goroutine 里的 data++、if 判断、以及 Printf 读取 data。

一种保护临界区的办法是同步对内存的访问。下面的代码不是地道的 Go 写法，只是为了演示概念：

var memoryAccess sync.Mutex // ① 用来同步对 value 内存访问的「锁」
var value int
go func() {
	memoryAccess.Lock()   // ② 从这里开始，我独占这块内存
	value++
	memoryAccess.Unlock() // ③ 用完了，释放
}()

memoryAccess.Lock() // ④ 下面的判断和打印也需要独占
if value == 0 {
	fmt.Printf("the value is %v.\n", value)
} else {
	fmt.Printf("the value is %v.\n", value)
}
memoryAccess.Unlock() // ⑤ 释放

我们在这里创建了一个约定：任何人想访问 value 的内存，必须先 Lock，用完 Unlock。 注意两点：

  1. 约定是可以被无视的。如果有人不遵守，就没有任何独占保证。你得指望所有开发者现在和将来都守规矩 —— 这要求很高（第 4 章的「约束」会给出更好的办法）。
  2. 数据竞争解决了，竞态条件没解决！到底是 goroutine 先执行，还是 if/else 先执行，依然不确定。我们只是把不确定的范围缩小了。

此外，加锁还有性能代价。每次 Lock 都可能让程序停顿一下。于是又带来两个需要权衡的问题：

  • 临界区是不是被频繁地进入和退出？
  • 临界区应该多大？

在你的程序里回答好这两个问题是一门手艺。下面这类问题，则是内存同步和其他并发建模方式共同面临的。

死锁（Deadlock）

前面几节讨论的是正确性：处理好它们，程序就不会给出错误答案。但还有一类问题关乎程序是否一直在做有用的事：死锁、活锁和饥饿。

死锁：所有并发进程都在互相等待，没有外力介入就永远无法恢复。 Go 运行时能检测出一部分死锁（所有 goroutine 都阻塞时），但这对预防死锁帮助不大。 

type value struct {
	mu    sync.Mutex
	value int
}

var wg sync.WaitGroup
printSum := func(v1, v2 *value) {
	defer wg.Done()
	v1.mu.Lock()                // ① 进入 v1 的临界区
	defer v1.mu.Unlock()        // ② 函数返回前释放

	time.Sleep(2 * time.Second) // ③ 模拟工作（并触发死锁）
	v2.mu.Lock()
	defer v2.mu.Unlock()

	fmt.Printf("sum=%v\n", v1.value+v2.value)
}

var a, b value
wg.Add(2)
go printSum(&a, &b)
go printSum(&b, &a)  // 注意：参数顺序反过来了
wg.Wait()

fatal error: all goroutines are asleep - deadlock!
🔎 反讽：这个死锁例子本身有竞态

为了让例子简单，作者用 time.Sleep 来「触发」死锁 —— 这本身就引入了竞态条件！理论上，一个 goroutine 完全可能在另一个开始之前就拿到并释放了两把锁，从而躲过死锁。「完美」的死锁需要正确的同步才能稳定复现。

1971 年，Edgar Coffman 总结了死锁发生的四个必要条件，现在称为科夫曼条件（Coffman Conditions）：

条件含义在上面的例子里
互斥一个资源同一时刻只能被一个并发进程独占printSum 需要独占 a 和 b
持有并等待进程拿着一个资源，同时等待另一个资源拿着 a（或 b），等另一个
不可抢占资源只能由持有者自己释放没有任何机制能强制夺走锁
环形等待P1 等 P2，P2（经过一条链）又在等 P1两个调用互相等待
★ 破坏任意一个条件，就能防止死锁

最常用的是破坏「环形等待」：所有人都按同一个顺序加锁（比如总是先锁地址小的那个，或按 ID 排序）。 可惜在实际代码中这些条件常常很难推理，网上满是「为什么这段代码会死锁」的提问 —— 往往别人一指就明白，但自己就是看不出来。

🆕 新版 Go：能检测「部分死锁」了 Go 1.26 实验 / 1.27

书中脚注提到，运行时只能检测「所有 goroutine 都睡着」的全局死锁，检测部分死锁的提案（issue 13759）尚未实现。 这件事在近两个版本有了进展：Go 1.26 以实验特性（GOEXPERIMENT=goroutineleakprofile）引入、Go 1.27 中默认可用的 goroutineleak 性能剖析，会借助垃圾回收找出「永远阻塞在不可达的通道或锁上」的 goroutine。 用法见附录 A。注意它只能发现阻塞在已经没人能访问到的同步原语上的情况，并不是万能的死锁检测器。

活锁（Livelock）

活锁：程序在积极地执行并发操作，但这些操作对推进程序状态毫无作用。

你一定遇到过：走廊里迎面走来一个人，她往一边让，你也正好往同一边让；你换到另一边，她也换了过来…… 如果这样永远继续下去，就是活锁。来用代码模拟一下： 

cadence := sync.NewCond(&sync.Mutex{})
go func() {
	for range time.Tick(1 * time.Millisecond) {
		cadence.Broadcast() // 每毫秒「打一次拍子」，让所有人步调一致
	}
}()

takeStep := func() {
	cadence.L.Lock()
	cadence.Wait() // 等下一拍
	cadence.L.Unlock()
}

// tryDir 尝试往某个方向走，返回是否成功。
// dir 记录「有多少人想往这个方向走」。
tryDir := func(dirName string, dir *int32, out *bytes.Buffer) bool {
	fmt.Fprintf(out, " %v", dirName)
	atomic.AddInt32(dir, 1)   // ① 宣布：我要往这边走
	takeStep()                // ② 所有人以相同节奏迈步
	if atomic.LoadInt32(dir) == 1 {
		fmt.Fprint(out, ". Success!")
		return true
	}
	takeStep()
	atomic.AddInt32(dir, -1)  // ③ 发现走不通，放弃这个方向
	return false
}

var left, right int32
tryLeft := func(out *bytes.Buffer) bool { return tryDir("left", &left, out) }
tryRight := func(out *bytes.Buffer) bool { return tryDir("right", &right, out) }

walk := func(walking *sync.WaitGroup, name string) {
	var out bytes.Buffer
	defer func() { fmt.Println(out.String()) }()
	defer walking.Done()
	fmt.Fprintf(&out, "%v is trying to scoot:", name)
	for i := 0; i < 5; i++ { // ① 人为限制尝试次数，否则程序永远不会结束
		if tryLeft(&out) || tryRight(&out) { // ② 先试左边，不行再试右边
			return
		}
	}
	fmt.Fprintf(&out, "\n%v tosses her hands up in exasperation!", name)
}

var peopleInHallway sync.WaitGroup // ③ 等两个人都通过或都放弃
peopleInHallway.Add(2)
go walk(&peopleInHallway, "Alice")
go walk(&peopleInHallway, "Barbara")
peopleInHallway.Wait()

Alice is trying to scoot: left right left right left right left right left right
Alice tosses her hands up in exasperation!
Barbara is trying to scoot: left right left right left right left right left right
Barbara tosses her hands up in exasperation!

这个例子展示了活锁最常见的成因：两个或多个并发进程都试图预防死锁，却没有相互协调。 作者认为活锁比死锁更难发现，因为程序看起来在干活：看 CPU 占用率，它确实很忙；它甚至可能输出各种「我在工作」的信号。

饥饿（Starvation）

饥饿：一个并发进程拿不到完成工作所需的全部资源。活锁其实是饥饿的一个子集 —— 只不过在活锁里，所有进程「饿得一样」，谁都没干成活。 更常见的饥饿是：有一个或多个贪婪的进程不公平地阻止了其他进程高效工作。 

var wg sync.WaitGroup
var sharedLock sync.Mutex
const runtime = 1 * time.Second

greedyWorker := func() {
	defer wg.Done()
	var count int
	for begin := time.Now(); time.Since(begin) <= runtime; {
		sharedLock.Lock()
		time.Sleep(3 * time.Nanosecond) // 一次锁住，干完 3ns 的活
		sharedLock.Unlock()
		count++
	}
	fmt.Printf("Greedy worker was able to execute %v work loops\n", count)
}

politeWorker := func() {
	defer wg.Done()
	var count int
	for begin := time.Now(); time.Since(begin) <= runtime; {
		sharedLock.Lock()               // 只在需要时加锁：
		time.Sleep(1 * time.Nanosecond) // 分三次，每次 1ns
		sharedLock.Unlock()

		sharedLock.Lock()
		time.Sleep(1 * time.Nanosecond)
		sharedLock.Unlock()

		sharedLock.Lock()
		time.Sleep(1 * time.Nanosecond)
		sharedLock.Unlock()
		count++
	}
	fmt.Printf("Polite worker was able to execute %v work loops.\n", count)
}

wg.Add(2)
go greedyWorker()
go politeWorker()
wg.Wait()

Polite worker was able to execute 289777 work loops.
Greedy worker was able to execute 471287 work loops

不要得出「贪婪算法更高效」或「Lock/Unlock 很慢」的结论（它们不慢）。正确的结论是：贪婪 worker 不必要地把锁的持有范围扩大到了临界区之外， 通过饥饿阻碍了礼貌 worker 的工作。

注意我们是怎么发现饥饿的：靠一个指标（metric）。这是记录和采样指标的好理由 —— 记录工作完成的时刻，再看工作速率是否符合预期。

✓ 寻找平衡：粗粒度 vs 细粒度

这个例子也说明了内存同步的性能代价。把锁的范围扩大（粗粒度）可能对性能有利，但会让别人挨饿； 范围小（细粒度）对公平有利。作者建议：一开始只在临界区加锁；如果同步真的成了性能瓶颈，再扩大范围。反过来收窄要难得多。

饥饿也可能来自 Go 进程之外：CPU、内存、文件句柄、数据库连接 —— 任何需要共享的资源都可能被「饿」到。

🆕 新版 Go：Mutex 有了「饥饿模式」 Go 1.9+

书出版后不久，Go 1.9 给 sync.Mutex 加入了饥饿模式：如果某个等待者等锁超过 1ms， 锁会切换到饥饿模式，此时解锁者把锁直接交给队首的等待者，新来的 goroutine 不能插队，直到饥饿解除。 所以在新版 Go 上跑这个例子，两个 worker 的差距通常会小一些（具体数字取决于机器）。但这不改变本节的结论： 锁的范围应该只覆盖临界区，而饥饿要靠指标来发现。

确定并发安全

最后，也是最难的一点：人。每行代码背后至少有一个人。作为调用者，你常常看不出一段代码是否用了并发、该怎样安全地使用它。看这个签名： 

// CalculatePi calculates digits of Pi between the begin and end
// place.
func CalculatePi(begin, end int64, pi *Pi)

它引出一连串问题：

  • 我要怎样用它并发地计算？
  • 需要我自己启动多个并发调用吗？
  • 所有调用都在直接操作我传进去的那个 *Pi，我要负责同步对它的访问吗？还是 Pi 类型自己处理了？

注释可以创造奇迹：

// CalculatePi calculates digits of Pi between the begin and end
// place.
//
// Internally, CalculatePi will create FLOOR((end-begin)/2) concurrent
// processes which recursively call CalculatePi. Synchronization of
// writes to pi are handled internally by the Pi struct.
func CalculatePi(begin, end int64, pi *Pi)
★ 涉及并发的 API，注释要回答三个问题
  1. 谁负责并发？（函数内部会启动 goroutine，还是要调用者自己开？）
  2. 问题空间是怎样映射到并发原语上的？
  3. 谁负责同步？

也许这种模糊本身说明我们建模错了。换一种函数式的思路，让函数没有副作用，甚至用返回类型来传递信号：

这些改动也会带来性能上的影响，我们又回到了清晰与性能之间的权衡。清晰很重要，因为我们希望将来维护代码的人尽可能做对的事； 性能的重要性则不言而喻。两者并不互斥，但很难兼顾。再把这些沟通上的难题放大到整个团队 —— 哇，这真是个问题。

🆕 新版 Go：不需要并发时，考虑迭代器 Go 1.23+

「返回通道」在书里是表达「这是一个数据流」的惯用法。但如果数据流只是为了逐个产出值、并不需要并发， Go 1.23 起更推荐返回迭代器 iter.Seq[uint]，调用者照样用 for d := range CalculatePi(b, e) 遍历， 却没有 goroutine 和通道的开销，也不用担心 goroutine 泄漏。返回通道，则明确表示「背后真的有并发」。

在复杂性面前保持简单

前面描绘的图景相当灰暗，但作者想给你希望：这些问题并非无解。Go 没有「解决」它们，但让它们容易得多。 Go 的运行时承担了大部分重活（第 6 章详解），这里先说它怎样让你的生活变轻松。

♻

并发、低延迟的垃圾回收器

内存管理本身就难，和并发混在一起更难。Go 1.8 时 GC 停顿已经在 10–100 微秒级别。你不必在并发进程之间手动管理内存。

🧶

自动把 goroutine 复用到线程上

不必自己创建线程池、把连接分配到线程、再让每个连接「可暂停」以便公平分享 CPU。

🔗

可组合的通道

通道是一种并发安全、可以组合的通信方式，让「把大问题拆成小问题」变得容易。

🆕 新版 Go：垃圾回收继续进化 Go 1.26+

书中「Go 1.8 的 GC 停顿在 10–100 微秒」的说法今天依然成立，而且 GC 在吞吐上还在持续改进： Go 1.26 默认启用了新的 Green Tea 垃圾回收器，对大量小对象的场景更友好，可以通过 GOEXPERIMENT=nogreenteagc 关闭。 对大多数并发程序来说，你依然完全不需要关心 GC 细节。

问题一句话描述典型对策
竞态条件操作顺序没有保证建立明确的同步点（join point），别用 sleep
数据竞争并发读写同一变量且没有同步互斥锁、通道、约束；用 -race 检测
原子性「一步」其实是多步，会被插入先定义上下文；用锁或 sync/atomic
死锁互相等待，永不恢复打破科夫曼条件之一，如统一加锁顺序
活锁很忙，但没进展协调各方，而不是各自「礼让」
饥饿资源被贪婪者霸占锁只覆盖临界区；用指标监控工作速率
