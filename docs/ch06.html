第 6 章

goroutine 与 Go 运行时

在 Go 里用并发很爽，因为语言把它变得太简单了，我们很少需要了解运行时在底下是怎样把一切缝合起来的。 但第 2 章讲的那些好处，全都是运行时的功劳。这一章掀开盖子，看看 Go 怎样把成千上万个 goroutine 高效地调度到少数几个线程上 —— 这既有用，也很有趣。

本章目标

  • 理解为什么「公平调度」和「中央队列」在 fork-join 模型下表现不佳
  • 掌握工作窃取（work stealing）算法的四条规则，并能一步步推演
  • 理解「窃取任务」和「窃取延续」的区别，以及书中的观点与当前运行时实现的差异
  • 认识调度器的 G、M、P 三个概念，以及系统调用、全局队列、抢占这些优化

先看几种「天真」的调度策略

第 2、3 章说过，Go 会替你把 goroutine 复用到操作系统线程上，它用的算法叫工作窃取（work stealing）。在讲它之前，先看看几种更简单的方案为什么不够好。

公平调度

为了让所有处理器都被平均利用，最简单的办法是把负载均分：有 n 个处理器、x 个任务，每个处理器分 x/n 个。比如两个处理器 P1、P2，四个任务 T1～T4，P1 拿 T1、T3，P2 拿 T2、T4。

问题在于 Go 使用 fork-join 模型：任务之间很可能互相依赖，简单地切分会让某个处理器闲着，还会破坏缓存局部性（需要相同数据的任务被分到了别的处理器上）。看两种情况：

第二种情况下，P1 被 T1 阻塞时，本可以先去做 T4 来解除自己的阻塞。

中央 FIFO 队列

听起来是负载均衡问题，用一个 FIFO 队列试试：任务进队列，处理器有空就出队取任务，或在汇合点阻塞。这是第一种工作窃取算法。 它解决了处理器闲置的问题，但引入了一个所有处理器都要使用的中心化数据结构。第 1 章说过，频繁进出临界区代价很高；而且缓存局部性更差了：每个处理器每次入队出队都要把这个中央队列加载到自己的缓存里。 对粗粒度的操作这也许可行，但 goroutine 通常是细粒度的，所以中央队列不是好选择。

下一步是去中心化：给每个处理器一个线程和一个双端队列（deque）。高争用的中央数据结构没了，但新问题来了： 如果工作从 P1 开始，所有 fork 出来的任务都放在 P1 的队列里，工作怎么流到 P2？任务在队列之间移动，会不会又有上下文切换的问题？

工作窃取的四条规则

回忆一下：Go 遵循 fork-join 模型。fork 是启动 goroutine；汇合点（join point）是两个或多个 goroutine 通过通道或 sync 包里的类型同步的地方。 对一个执行线程来说，工作窃取算法遵循几条基本规则：

  1. 在 fork 点，把任务加到当前线程的 deque 的尾部；
  2. 如果线程空闲，从随机选择的另一个线程的 deque 头部偷取工作；
  3. 在一个还无法实现的汇合点（与之同步的 goroutine 还没完成），从自己 deque 的尾部弹出工作；
  4. 如果自己的 deque 空了：要么 a) 在汇合点停顿（stall），要么 b) 从随机另一个线程的 deque 头部偷取工作。

来看真实代码。下面的程序用递归计算斐波那契数列：

var fib func(n int) <-chan int
fib = func(n int) <-chan int {
	result := make(chan int)
	go func() {
		defer close(result)
		if n <= 2 {
			result <- 1
			return
		}
		result <- <-fib(n-1) + <-fib(n-2)
	}()
	return result
}

fmt.Printf("fib(4) = %d", <-fib(4))

假设程序跑在一台有两个单核处理器的假想机器上，每个处理器一个 OS 线程：T1 和 T2。下面一步步看工作窃取算法怎样运行这个程序（实际上这一切都不是确定的，这里为了说明选了一种可能的顺序）。 点击按钮逐步查看：

演示 1：窃取「任务」（goroutine）

工作在 deque 尾部有两个很有用的性质：

  • 它最可能是完成父亲的汇合所需要的工作。越快完成汇合，程序越可能跑得好，内存里需要保存的东西也越少。
  • 它最可能还在处理器的缓存里。它是线程在当前工作之前刚处理过的，数据很可能还在这个 CPU 的缓存中，缓存未命中更少。

总之，这样调度工作有很多隐含的性能好处。

窃取任务还是窃取延续？

一直没细说的问题是：我们入队和窃取的到底是什么？在 fork-join 模式下有两种选择：任务（task）和延续（continuation）。 再看一次斐波那契程序： 

var fib func(n int) <-chan int
fib = func(n int) <-chan int {
	result := make(chan int)
	go func() { // ← 在 Go 里，goroutine 就是「任务」
		defer close(result)
		if n <= 2 {
			result <- 1
			return
		}
		result <- <-fib(n-1) + <-fib(n-2)
	}()
	return result // ← go 语句之后的所有东西，就是「延续」
}

上面的推演里，我们入队和窃取的是任务（goroutine）。goroutine 很好地封装了一块工作，这是很自然的想法。但书中指出，Go 的工作窃取算法入队和窃取的是延续。这有什么区别？

在算法里，线程到达一个未实现的汇合点时，必须暂停执行、去找任务来偷，这叫停顿的汇合（stalling join）。任务窃取和延续窃取都会有停顿的汇合，但发生的频率差别很大。考虑这几条公理：

  • 创建 goroutine 时，程序很可能希望这个 goroutine 里的函数被执行；
  • 延续很可能在某个时刻要和这个 goroutine 汇合；
  • 延续在 goroutine 完成之前就尝试汇合，也很常见。

基于这些，调度 goroutine 时立即开始执行它是合理的。再结合「线程在自己队尾压入弹出、别人从队头偷」的性质：如果把延续压到队尾，它最不容易被从队头偷的其他线程偷走， 于是执行完 goroutine 后很可能直接把它拿回来继续，避免停顿。这让 fork 出来的任务看起来很像一次函数调用：线程跳去执行 goroutine，结束后再回到延续。 用延续窃取重新推演一遍（入队的延续记作「cont. of X」）：

综合来看，窃取延续在理论上优于窃取任务。为什么不是所有工作窃取算法都这样实现？因为延续窃取通常需要编译器的支持。 书中认为 Go 有自己的编译器，所以 Go 的工作窃取算法实现的是延续窃取；没有这种条件的语言通常以库的形式实现任务（即「子任务」）窃取。

🔎 勘误与补充：今天的 Go 运行时其实是怎样做的

书中「Go 窃取的是延续」的说法，与当前 Go 运行时的源码并不一致，请把它理解为一种理论模型。查看 Go 1.27 的 runtime/proc.go： go 语句编译为对 newproc 的调用，它创建新的 G，然后执行 runqput(pp, newg, true) —— 把新 goroutine（子任务）放进当前 P 的 runnext 槽位，父 goroutine（延续）继续运行。 当父 goroutine 很快在汇合点阻塞（比如等通道）时，P 会优先运行 runnext 里的那个新 goroutine，于是同样获得了「刚创建的工作马上在同一个 CPU 上执行」的缓存局部性； 空闲的 P 则从别的 P 的本地队列偷走一半的 goroutine。也就是说，Go 实际做的是带 runnext 优化的「子任务窃取」，书中对延续窃取优势的分析，在思想层面仍然有助于理解调度器为什么要这样设计。

G、M、P：Go 调度器的三个概念

上面的模型已经很接近 Go 的算法，但还不是全貌，Go 还做了额外的优化。先换用 Go 调度器源码里的术语：

G
一个 goroutine。注意它代表 goroutine 的当前状态，尤其是程序计数器（PC）。
M
一个 OS 线程（源码里也叫 machine）。
P
一个上下文（源码里也叫 processor）。

在前面的讨论里，M 相当于 T，P 相当于工作队列（调整 GOMAXPROCS 改变的就是 P 的数量）。运行时启动若干 M，M 承载 P，P 再调度和承载 G：

GOMAXPROCS 控制运行时可用的上下文（P）数量，默认每个逻辑 CPU 一个。和 P 不同，OS 线程（M）可以比核数多或少，以便运行时处理垃圾回收、goroutine 等事务。 运行时有一个非常重要的保证：总有足够的 OS 线程来承载每一个上下文。运行时还有一个线程池，存放暂时不用的线程。这让下面的优化成为可能。

系统调用：把 P 交出去

如果某个 goroutine 因为 I/O 或调用 Go 运行时之外的系统调用而阻塞，承载它的 OS 线程也会被阻塞，无法推进也无法承载别的 goroutine。逻辑上没问题， 但从性能上看，Go 可以做得更好，让机器上的处理器尽量保持忙碌。

Go 的做法是：把上下文（P）从被阻塞的 OS 线程上分离，交给另一个未阻塞的线程，让这个 P 继续调度其他 goroutine，宿主机的 CPU 保持活跃。被阻塞的 goroutine 仍然和那个被阻塞的线程绑在一起。 当 goroutine 最终解除阻塞，宿主线程会尝试从其他线程那里偷回一个上下文，继续执行它。如果偷不到，线程就把 goroutine 放到全局上下文（全局队列）里，自己去睡觉，进入线程池以备将来使用。

全局队列在前面抽象的工作窃取算法里没有出现，它是 Go 为优化 CPU 利用率而引入的实现细节。为了保证放到全局队列里的 goroutine 不会永远待在那里，算法里加了几步： 上下文会定期检查全局队列；当自己的队列空了时，会先看全局队列，再去偷别的线程的工作。

抢占

除了 I/O 和系统调用，Go 还允许 goroutine 在任何函数调用时被抢占。这与 Go 偏爱细粒度并发任务的理念相配合，保证运行时能高效地调度工作。 书中提到一个 Go 团队当时正在解决的例外：既没有 I/O、没有系统调用、也没有函数调用的 goroutine（比如一个紧密的纯计算循环）不可抢占，可能导致很长的 GC 等待，甚至死锁。

🆕 新版 Go：异步抢占解决了这个问题 Go 1.14+

书中提到的问题已经在 Go 1.14 解决：运行时会定期检查运行太久（约 10ms）的 goroutine，通过向线程发送信号（Unix 上是 SIGURG）异步抢占它， 即使是没有函数调用的死循环也能被打断。所以今天「一个 goroutine 霸占线程、让 GC 等很久」的情况基本不会再出现。

把这一切呈现给开发者

了解了 goroutine 在底层怎样工作，再退一步看开发者是怎样和这一切打交道的：就是 go 关键字。没了！ 在函数或闭包前加个 go，就自动调度了一个任务，它会以最适合所在机器的方式高效运行。作为开发者，我们依然用熟悉的原语 —— 函数 —— 来思考， 不需要理解新的做事方式、复杂的数据结构或调度算法。

🆕 新版 Go：亲眼看看调度器在做什么
  • GODEBUG=schedtrace=1000 ./prog：每秒打印一次调度器状态（每个 P 的本地队列长度、全局队列长度、线程数等）；加上 scheddetail=1 会更详细。
