第 3 章

Go 的并发构件

从这一章开始写代码。我们会逐一认识 Go 提供的并发「积木」：goroutine、sync 包里的 WaitGroup、Mutex、Cond、Once、Pool， 以及通道（channel）和 select。如果你之前没在 Go 里写过并发，这一章就是起点。

本章目标

  • 会启动 goroutine，理解 fork-join 模型和「汇合点」
  • 理解闭包捕获变量的行为，以及 Go 1.22 对循环变量的修改
  • 知道 sync 包里每种原语解决什么问题、有哪些坑
  • 熟练掌握通道的阻塞、关闭、缓冲、nil 通道等全部行为，并学会「通道所有权」
  • 会用 select 实现等待多个事件、超时和非阻塞操作

goroutine

goroutine 是 Go 程序最基本的组织单位之一。每个 Go 程序至少有一个 goroutine：主 goroutine，进程启动时自动创建。 简单地说，goroutine 就是一个与其他代码并发运行（记住：不一定并行！）的函数。在函数调用前加上 go 关键字就能启动一个： 

func main() {
	go sayHello()
	// 继续做别的事
}

func sayHello() {
	fmt.Println("hello")
}

匿名函数也可以（注意必须立即调用，即末尾的 ()）；也可以先把函数赋给变量再调用：

匿名函数
go func() {
	fmt.Println("hello")
}()
// 继续做别的事
函数变量
sayHello := func() {
	fmt.Println("hello")
}
go sayHello()
// 继续做别的事

就这么简单！一个关键字，就创建了一块并发逻辑。剩下的内容讲的是怎样正确地使用、同步和组织它们。

goroutine 到底是什么？

goroutine 不是操作系统线程，也不完全是「绿色线程」（由语言运行时管理的线程）。它是一种更高层的抽象，叫做协程（coroutine）。 协程是并发的子程序（函数、闭包或方法），它们是非抢占式的 —— 不能被打断，只能在若干「可以暂停或重入」的点上让出执行。

goroutine 的独特之处在于它和 Go 运行时的深度整合：goroutine 自己不定义暂停点，而是由运行时观察它的行为， 在它阻塞时自动挂起、解除阻塞时再恢复。从某种意义上说，这让它们变得可抢占，但只在阻塞的地方。

🆕 新版 Go：goroutine 现在几乎随处可被抢占 Go 1.14+

书中描述的是 Go 1.13 及以前的「协作式」调度：goroutine 只在阻塞、系统调用或函数调用时才可能被换下。 Go 1.14 引入了基于信号的异步抢占：一个长时间运行、甚至没有任何函数调用的紧密循环，也会被运行时强行打断， 不会再霸占线程、拖慢垃圾回收甚至造成卡死。第 6 章会再提到这一点。

Go 托管 goroutine 的机制是一个 M:N 调度器：把 M 个绿色线程映射到 N 个操作系统线程上，goroutine 再被调度到这些绿色线程上。 goroutine 比可用线程多时，调度器负责分配，并保证某些 goroutine 阻塞时，其他的还能运行。

fork-join 模型与汇合点

Go 遵循 fork-join（分叉—汇合）并发模型。fork 指程序在任何时刻都可以分出一个子执行分支，与父分支并发运行； join 指未来某个时刻这些分支会重新汇合。子分支重新汇入父分支的地方叫做汇合点（join point）。 go 语句就是 Go 执行 fork 的方式，分出来的执行线索就是 goroutine。

回到最初的例子：sayHello 在自己的 goroutine 里运行，程序继续往下走，没有汇合点。 这有一个问题：sayHello 到底会不会运行是不确定的。goroutine 被创建并交给运行时调度，但可能还没轮到它，主 goroutine 就退出了。 在 go 之后加个 time.Sleep？回忆第 1 章：那只是竞态条件，不是汇合点。我们需要的是同步。这里先用 sync.WaitGroup（稍后详解）： 

var wg sync.WaitGroup
sayHello := func() {
	defer wg.Done()
	fmt.Println("hello")
}
wg.Add(1)
go sayHello()
wg.Wait() // ← 这里就是汇合点

这个程序会确定地阻塞主 goroutine，直到 sayHello 所在的 goroutine 结束，输出 hello。

goroutine 与闭包

闭包会「包住」它被创建时的词法作用域，从而捕获变量。在 goroutine 里运行闭包时，闭包操作的是变量的副本，还是原变量本身？试一下： 

var wg sync.WaitGroup
salutation := "hello"
wg.Add(1)
go func() {
	defer wg.Done()
	salutation = "welcome" // goroutine 修改了外面的变量
}()
wg.Wait()
fmt.Println(salutation) // 输出：welcome

输出 welcome。goroutine 和创建它的代码运行在同一个地址空间里，闭包拿到的是原变量。再看一个更微妙的例子： 

var wg sync.WaitGroup
for _, salutation := range []string{"hello", "greetings", "good day"} {
	wg.Add(1)
	go func() {
		defer wg.Done()
		fmt.Println(salutation) // 引用了循环变量
	}()
}
wg.Wait()

good day
good day
good day

很多人以为会以某种顺序打印三个不同的词，结果却是三个 good day。原因是：在旧版 Go 里， 整个循环只有一个 salutation 变量，每轮迭代只是给它赋新值。goroutine 可能在未来任何时候才运行， 在作者的机器上，循环往往在任何 goroutine 开始之前就结束了，此时 salutation 的值是最后一个 "good day"。

循环结束后变量不是「出作用域」了吗？goroutine 还能访问吗？这里体现了 Go 的内存管理：编译器注意到这个变量仍被引用， 于是把它的内存转移到堆上（逃逸分析），goroutine 可以继续安全访问。书中的正确写法是把当前值作为参数传进去，让每个 goroutine 拿到自己的副本： 

var wg sync.WaitGroup
for _, salutation := range []string{"hello", "greetings", "good day"} {
	wg.Add(1)
	go func(salutation string) { // ① 声明参数，故意与外层同名（遮蔽）
		defer wg.Done()
		fmt.Println(salutation)
	}(salutation) // ② 把本轮的值复制进去
}
wg.Wait()
🆕 新版 Go：循环变量每轮迭代都是新的 Go 1.22+

Go 1.22 修改了 for 循环的语义：用 := 声明的循环变量每轮迭代都是一个新变量。 所以在 go.mod 声明 go 1.22 或更高的模块里，上面「错误」的版本也会正确打印三个不同的词（顺序不定）。 书中「把值作为参数传进去」的写法依然正确，但已经不再必要。注意这个行为由模块的 go 版本决定，而不是你安装的 Go 版本： 老模块升级时，可以用 go vet 的 loopclosure 检查或 bisect 工具排查受影响的代码。 

var wg sync.WaitGroup
for _, salutation := range []string{"hello", "greetings", "good day"} {
	wg.Go(func() { // Go 1.25+：自动 Add(1)，函数返回时自动 Done()
		fmt.Println(salutation) // 每轮迭代独立的变量，放心引用
	})
}
wg.Wait()

因为 goroutine 共享地址空间、只是托管函数，使用 goroutine 是编写非并发代码的自然延伸。编译器会把变量「钉」在内存里，避免 goroutine 访问已释放的内存， 让你专注于问题本身。但这不是空白支票：多个 goroutine 可以操作同一块内存，我们仍然需要同步 —— 要么同步对共享内存的访问，要么用 CSP 原语通过通信来共享内存。

goroutine 有多轻？

Go FAQ 里这样写：

新创建的 goroutine 只分配几 KB 的栈，这几乎总是够用的；不够时，运行时会自动增长（和收缩）栈。CPU 开销平均每次函数调用约三条廉价指令。 在同一地址空间里创建几十万个 goroutine 是现实可行的。如果 goroutine 只是线程，系统资源会在小得多的数量上耗尽。

动手验证之前，先说一个重要事实：垃圾回收器不会回收被遗弃的 goroutine。如果写了下面这样的代码，这个 goroutine 会一直存在到进程退出： 

go func() {
	// <一个会永远阻塞的操作>
}()
// 做其他事

第 4 章「防止 goroutine 泄漏」会解决这个问题。这里正好利用它来测量 goroutine 的大小：

memConsumed := func() uint64 {
	runtime.GC()
	var s runtime.MemStats
	runtime.ReadMemStats(&s)
	return s.Sys
}

var c <-chan interface{}
var wg sync.WaitGroup
noop := func() { wg.Done(); <-c } // ① 从 nil 通道读，永远阻塞，goroutine 不会退出

const numGoroutines = 1e4 // ② 用大数定律逼近单个 goroutine 的大小
wg.Add(numGoroutines)
before := memConsumed() // ③ 创建前
for i := numGoroutines; i > 0; i-- {
	go noop()
}
wg.Wait()
after := memConsumed() // ④ 创建后
fmt.Printf("%.3fkb", float64(after-before)/numGoroutines/1000)

书中结果是 2.817kb，按此推算，8 GB 内存理论上能容纳几百万个 goroutine。在本笔记写作时用 Go 1.27 实测是 2.55kb 左右。

另一个可能让人担心的是上下文切换：并发进程切换时要保存状态、再加载另一个的状态。OS 线程切换要保存寄存器、查找表、内存映射等，代价不小。 软件定义的调度器可以更挑剔地决定保存什么、怎么保存、什么时候保存。书中用 Linux 的 perf bench sched pipe 测得线程切换约 1.467μs， 再用下面的基准测试测 goroutine： 

func BenchmarkContextSwitch(b *testing.B) {
	var wg sync.WaitGroup
	begin := make(chan struct{})
	c := make(chan struct{})

	var token struct{}
	sender := func() {
		defer wg.Done()
		<-begin // ① 等发令枪，不把创建 goroutine 的开销算进来
		for i := 0; i < b.N; i++ {
			c <- token // ② struct{}{} 不占内存，只测「发信号」的开销
		}
	}
	receiver := func() {
		defer wg.Done()
		<-begin
		for i := 0; i < b.N; i++ {
			<-c // ③ 收到消息，什么都不做
		}
	}

	wg.Add(2)
	go sender()
	go receiver()
	b.StartTimer() // ④ 开始计时
	close(begin)   // ⑤ 发令：两个 goroutine 同时开始
	wg.Wait()
}

★ goroutine 很便宜

只要你的问题没有被阿姆达尔定律里的某个顺序段卡住，goroutine 越多，程序就越能利用多处理器扩展。 创建 goroutine 非常便宜，只有在你证明了它们是性能问题的根源时，才需要讨论它们的成本。

sync 包

sync 包包含了最适合底层内存访问同步的并发原语。如果你用过以内存同步为主的语言，这些类型会很眼熟。 不同的是，Go 在它们之上又构建了一套新的原语（通道等）。正如第 2 章所说，它们最适合用在小作用域里，比如一个结构体内部。

WaitGroup

当你不关心并发操作的结果，或者有其他办法收集结果时，WaitGroup 是等待一组并发操作完成的好办法。 如果两个条件都不满足，作者建议改用通道和 select。 

var wg sync.WaitGroup

wg.Add(1) // ① 一个 goroutine 要开始了
go func() {
	defer wg.Done() // ② 用 defer 保证退出前一定通知「我结束了」
	fmt.Println("1st goroutine sleeping...")
	time.Sleep(1)
}()

wg.Add(1)
go func() {
	defer wg.Done()
	fmt.Println("2nd goroutine sleeping...")
	time.Sleep(2)
}()

wg.Wait() // ③ 阻塞，直到所有 goroutine 都报告结束
fmt.Println("All goroutines complete.")
⚠ Add 必须在 goroutine 外面调用

注意 Add 是在它要跟踪的 goroutine 之外调用的。如果放进 goroutine 里，就引入了竞态： 我们无法保证 goroutine 什么时候被调度，可能在任何一个 Add 执行之前就走到了 Wait，于是 Wait 直接返回，根本没等。

习惯上 Add 尽量紧挨着它跟踪的 goroutine，但有时也会在循环前一次性加好：

hello := func(wg *sync.WaitGroup, id int) {
	defer wg.Done()
	fmt.Printf("Hello from %v!\n", id)
}

const numGreeters = 5
var wg sync.WaitGroup
wg.Add(numGreeters) // 一次性加 5
for i := 0; i < numGreeters; i++ {
	go hello(&wg, i+1)
}
wg.Wait()
🆕 新版 Go：wg.Go 与 vet 检查 Go 1.25+

Go 1.25 给 WaitGroup 加了 Go(f func()) 方法：它在新 goroutine 里运行 f，自动完成 Add(1) 和 Done()， 从结构上消除了「忘记 Done」「Add 放错位置」两类 bug。同时 go vet 新增了 waitgroup 检查， 会对「在新 goroutine 里调用 wg.Add」报错：WaitGroup.Add called from inside new goroutine。 

var wg sync.WaitGroup
for i := range 5 { // Go 1.22+：可以 range 一个整数
	wg.Go(func() {
		fmt.Printf("Hello from %v!\n", i+1)
	})
}
wg.Wait()

如果 goroutine 可能出错、需要收集第一个错误或出错时取消其他任务，用 golang.org/x/sync/errgroup（第 5 章会再提到）。

Mutex 和 RWMutex

Mutex 是「mutual exclusion（互斥）」的缩写，用来保护程序的临界区。借用 Go 的说法：通道通过通信来共享内存， 而 Mutex 通过开发者必须遵守的约定来共享内存 —— 你负责用锁守住对内存的访问。 

var count int
var lock sync.Mutex

increment := func() {
	lock.Lock()         // ① 请求独占 count 这个临界区
	defer lock.Unlock() // ② 用完释放
	count++
	fmt.Printf("Incrementing: %d\n", count)
}

decrement := func() {
	lock.Lock()
	defer lock.Unlock()
	count--
	fmt.Printf("Decrementing: %d\n", count)
}

// 增加
var arithmetic sync.WaitGroup
for i := 0; i <= 5; i++ {
	arithmetic.Add(1)
	go func() {
		defer arithmetic.Done()
		increment()
	}()
}

// 减少
for i := 0; i <= 5; i++ {
	arithmetic.Add(1)
	go func() {
		defer arithmetic.Done()
		decrement()
	}()
}

arithmetic.Wait()
fmt.Println("Arithmetic complete.")

输出的中间值顺序不定，但最后一定回到 0。注意 Unlock 总是放在 defer 里 —— 这是使用 Mutex 的惯用法，保证即使发生 panic 也一定会解锁。忘了解锁，程序多半会死锁。

🆕 新版 Go：defer 几乎零开销 Go 1.14+

早年有人为了性能在热点路径上避免 defer Unlock()。Go 1.14 引入了「开放编码的 defer」，大多数情况下 defer 的开销已接近直接调用， 请放心使用 defer mu.Unlock()。另外 Go 1.18 加了 TryLock，但官方文档明确说「正确使用它的场景很少见」，通常意味着设计有问题。

临界区之所以叫「临界」，是因为它们反映了程序的瓶颈：进出临界区有一定开销，所以大家都想尽量缩短在临界区里的时间。 一种策略是缩小临界区的「截面」：也许很多并发进程都要访问某块内存，但并不是所有人都要写。这时可以用 sync.RWMutex： 可以同时有任意多个读者持有读锁，只要没有人持有写锁。

书中用一个基准对比了两者：一个不太活跃的生产者（写者）和越来越多的观察者（读者）。

producer := func(wg *sync.WaitGroup, l sync.Locker) { // ① sync.Locker 接口：Lock() 和 Unlock()
	defer wg.Done()
	for i := 5; i > 0; i-- {
		l.Lock()
		l.Unlock()
		time.Sleep(1) // ② 让生产者比观察者更「懒」一些
	}
}

observer := func(wg *sync.WaitGroup, l sync.Locker) {
	defer wg.Done()
	l.Lock()
	defer l.Unlock()
}

test := func(count int, mutex, rwMutex sync.Locker) time.Duration {
	var wg sync.WaitGroup
	wg.Add(count + 1)
	beginTestTime := time.Now()
	go producer(&wg, mutex)
	for i := count; i > 0; i-- {
		go observer(&wg, rwMutex)
	}
	wg.Wait()
	return time.Since(beginTestTime)
}

✓ 补充：读多写少的 map 可以看看 sync.Map Go 1.9+

书中没有提到的 sync.Map 适合两种场景：键只写一次、读很多次（如缓存）；或多个 goroutine 读写互不相交的键。 其他情况下，普通 map 加 Mutex/RWMutex 往往更简单、类型更安全。Go 1.24 用新的并发哈希树重写了 sync.Map，性能有明显提升。

Cond

Cond 类型的注释很好地概括了它的用途：

……一个让 goroutine 等待某个事件发生、或宣布某个事件发生的会合点。

这里的「事件」是两个或多个 goroutine 之间的任意信号，除了「它发生了」之外不携带任何信息。经常需要等某个信号再继续执行。 不用 Cond 的话，一种天真的写法是死循环：

✗ 忙等：吃满一个核
for conditionTrue() == false {
}
✗ 睡一会儿：睡多久？
for conditionTrue() == false {
	time.Sleep(1 * time.Millisecond)
}

后者好一些，但仍然低效，而且得猜睡多久：太久会人为降低性能，太短又浪费 CPU。更好的办法是让 goroutine 高效地睡着，直到被通知醒来检查条件 —— 这正是 Cond 做的事： 

c := sync.NewCond(&sync.Mutex{}) // ① NewCond 接受一个满足 sync.Locker 接口的值
c.L.Lock()                        // ② 必须先加锁：Wait 进入时会自动 Unlock
for conditionTrue() == false {
	c.Wait()                      // ③ 挂起当前 goroutine，等待通知
}
c.L.Unlock()                      // ④ 必须解锁：Wait 返回时会自动重新 Lock

这种方式高效得多：Wait 不只是阻塞，而是挂起当前 goroutine，让其他 goroutine 可以在这个 OS 线程上运行。 作者坦言这个「隐藏的副作用」需要时间适应。

来看收发两端都有的例子：一个固定长度为 2 的队列，要放入 10 个元素，一有空位就立刻放：

c := sync.NewCond(&sync.Mutex{})    // ① 用普通 Mutex 作为 Locker
queue := make([]interface{}, 0, 10) // ② 长度 0、容量 10 的切片

removeFromQueue := func(delay time.Duration) {
	time.Sleep(delay)
	c.L.Lock()        // ⑧ 再次进入临界区，修改与条件相关的数据
	queue = queue[1:] // ⑨ 模拟出队
	fmt.Println("Removed from queue")
	c.L.Unlock()      // ⑩ 离开临界区
	c.Signal()        // ⑪ 通知一个正在等待的 goroutine：有事发生了
}

for i := 0; i < 10; i++ {
	c.L.Lock()            // ③ 进入临界区
	for len(queue) == 2 { // ④ 必须在循环里检查！收到信号只代表「有事发生」，不代表你等的条件已满足
		c.Wait()          // ⑤ 挂起主 goroutine，等信号
	}
	fmt.Println("Adding to queue")
	queue = append(queue, struct{}{})
	go removeFromQueue(1 * time.Second) // ⑥ 1 秒后出队一个元素
	c.L.Unlock()                        // ⑦ 入队成功，离开临界区
}

这里出现了 Signal，它是通知 Wait 中 goroutine 的两个方法之一，另一个是 Broadcast。 运行时内部维护了一个等待者的 FIFO 列表：Signal 唤醒等待最久的那一个；Broadcast 唤醒所有等待者。 用通道很容易模拟 Signal，但要模拟「反复 Broadcast」就难了；而且 Cond 的性能比通道好得多。

想象一个带按钮的 GUI 程序，我们想注册任意多个函数，按钮被点击时全部执行。Broadcast 再合适不过：

type Button struct { // ① Button 包含一个条件 Clicked
	Clicked *sync.Cond
}
button := Button{Clicked: sync.NewCond(&sync.Mutex{})}

subscribe := func(c *sync.Cond, fn func()) { // ② 每个处理函数跑在自己的 goroutine 里
	var goroutineRunning sync.WaitGroup
	goroutineRunning.Add(1)
	go func() {
		goroutineRunning.Done()
		c.L.Lock()
		defer c.L.Unlock()
		c.Wait()
		fn()
	}()
	goroutineRunning.Wait() // 确认 goroutine 已经跑起来才返回
}

var clickRegistered sync.WaitGroup // ③ 只为了保证程序不在输出前退出
clickRegistered.Add(3)
subscribe(button.Clicked, func() { // ④ 模拟最大化窗口
	fmt.Println("Maximizing window.")
	clickRegistered.Done()
})
subscribe(button.Clicked, func() { // ⑤ 模拟弹出对话框
	fmt.Println("Displaying annoying dialog box!")
	clickRegistered.Done()
})
subscribe(button.Clicked, func() { // ⑥ 模拟鼠标点击
	fmt.Println("Mouse clicked.")
	clickRegistered.Done()
})

button.Clicked.Broadcast() // ⑦ 模拟用户松开鼠标：一次通知所有处理函数
clickRegistered.Wait()

和 sync 包里大多数东西一样，Cond 最好用在很小的作用域里，或者被一个类型封装起来再暴露给更大的范围。

🔎 现实中 Cond 用得并不多

实践中，很多 Go 开发者更倾向于用通道表达「事件」：一次性的事件用 close(ch) 广播（本章「通道」一节会讲）， 需要携带数据就发送值。Cond 的一个难点是它不能和 select、超时、context 取消组合。 如果非用不可，可以借助 Go 1.21 的 context.AfterFunc 在 context 取消时 Broadcast 唤醒等待者（标准库文档中有示例）。

Once

猜猜这段代码会输出什么？

var count int
increment := func() {
	count++
}

var once sync.Once

var increments sync.WaitGroup
increments.Add(100)
for i := 0; i < 100; i++ {
	go func() {
		defer increments.Done()
		once.Do(increment)
	}()
}

increments.Wait()
fmt.Printf("Count is %d\n", count) // Count is 1

输出 Count is 1。sync.Once 内部用了一些同步原语，确保即使在不同 goroutine 上，对 Do 的调用只有一次会真正执行传入的函数。 这个需求出奇地常见：书中用 grep -ir sync.Once $(go env GOROOT)/src | wc -l 统计，Go 1.8 的标准库里出现了 70 次； 本笔记写作时在 Go 1.27 上再跑一次，已经是 305 次。

两个需要注意的地方。第一，看这个例子：

var count int
increment := func() { count++ }
decrement := func() { count-- }

var once sync.Once
once.Do(increment)
once.Do(decrement)

fmt.Printf("Count: %d\n", count) // Count: 1

结果是 1 而不是 0：sync.Once 只统计 Do 被调用了几次，不管传进去的是哪个函数。 所以一个 Once 和它要调用的函数是紧密绑定的。作者建议把 Once 的使用包在一个小的词法块里：一个小函数，或者和函数一起封装进一个类型。

第二，这个例子会怎样？

var onceA, onceB sync.Once
var initB func()
initA := func() { onceB.Do(initB) }
initB = func() { onceA.Do(initA) } // ① 这个调用要等 ② 返回才能继续
onceA.Do(initA)                    // ②

死锁：① 处的 Do 要等 ② 处的 Do 退出，而 ② 又在等 ①。 看起来我们在按预期用 Once 防止重复初始化，但 Once 唯一保证的是「函数只调用一次」—— 有时它是通过让程序死锁、暴露你的逻辑缺陷（这里是循环引用）来做到的。

🆕 新版 Go：OnceFunc / OnceValue / OnceValues Go 1.21+

作者建议「把 Once 和函数封装在一起」，Go 1.21 直接把这个建议做进了标准库： 

// 返回一个「只会执行一次」的函数，Once 和函数天然绑定在一起
initLogger := sync.OnceFunc(func() { /* ... */ })

// 懒加载一个值：第一次调用时计算，之后直接返回缓存结果
loadConfig := sync.OnceValue(func() *Config { return parseConfig() })
cfg := loadConfig()

// 带错误返回的版本
readKey := sync.OnceValues(func() ([]byte, error) {
	return os.ReadFile("key.pem")
})
key, err := readKey()

还有一个区别：如果函数 panic，OnceFunc 返回的函数在之后每次调用时都会以同样的值重新 panic，而 sync.Once.Do 之后的调用则静默地什么都不做。

Pool

Pool 是对象池模式的并发安全实现。对象池是一种创建并提供固定数量（池）的东西以供使用的方式， 常用于限制昂贵事物（如数据库连接）的创建数量。Go 的 sync.Pool 可以被多个 goroutine 安全使用。 它的主要接口是 Get：先看池里有没有可用实例，有就返回，没有就调用 New 创建一个。用完后调用 Put 放回去。 

myPool := &sync.Pool{
	New: func() interface{} {
		fmt.Println("Creating new instance.")
		return struct{}{}
	},
}

myPool.Get()             // ① 池是空的，调用 New
instance := myPool.Get() // ① 还是空的，再调用一次 New
myPool.Put(instance)     // ② 放回一个，池里有 1 个可用实例
myPool.Get()             // ③ 复用刚放回的实例，不调用 New

输出两行 Creating new instance.。为什么要用池，而不是随用随建？Go 有垃圾回收，对象会被自动清理。看这个例子： 

var numCalcsCreated int
calcPool := &sync.Pool{
	New: func() interface{} {
		numCalcsCreated += 1
		mem := make([]byte, 1024)
		return &mem // ① 存的是切片的地址
	},
}

// 先往池里预存 4KB
calcPool.Put(calcPool.New())
calcPool.Put(calcPool.New())
calcPool.Put(calcPool.New())
calcPool.Put(calcPool.New())

const numWorkers = 1024 * 1024
var wg sync.WaitGroup
wg.Add(numWorkers)
for i := numWorkers; i > 0; i-- {
	go func() {
		defer wg.Done()
		mem := calcPool.Get().(*[]byte) // ② 断言类型为 *[]byte
		defer calcPool.Put(mem)
		// 假设这里用这块内存快速地做了些有趣的事
	}()
}

wg.Wait()
fmt.Printf("%d calculators were created.", numCalcsCreated)

输出 8 calculators were created.（结果不确定）。不用 Pool 的话，最坏情况下可能要分配 1GB 内存（一百万个 goroutine 各 1KB）， 而这里只分配了约 8KB。

⚠ 书中这个例子有数据竞争

New 会被多个 goroutine 并发调用，而 numCalcsCreated += 1 没有任何同步。用 go run -race 运行会报告 DATA RACE。 （竞态检测模式下 Pool 还会故意随机丢弃对象以暴露 bug，所以打印的数字会大得多。）这正呼应了本节后面的规则：传给 New 的函数必须是并发安全的。修正方式： 

var numCalcsCreated atomic.Int64
calcPool := &sync.Pool{
	New: func() any { // Go 1.18+：any 是 interface{} 的别名
		numCalcsCreated.Add(1)
		mem := make([]byte, 1024)
		return &mem
	},
}

Pool 的另一个常见用途是预热一批预先分配好的对象，供必须尽快完成的操作使用。这时不是为了节省宿主机内存， 而是把「获取对象的时间」提前支付，为调用者节省时间。这在高吞吐网络服务里很常见。书中模拟了一个「连接到某个服务需要 1 秒」的场景： 

func connectToService() interface{} {
	time.Sleep(1 * time.Second) // 建立连接很慢
	return struct{}{}
}

func warmServiceConnCache() *sync.Pool {
	p := &sync.Pool{
		New: connectToService,
	}
	for i := 0; i < 10; i++ {
		p.Put(p.New()) // 启动时预先建立 10 个连接
	}
	return p
}

// 在网络守护进程的循环里：
for {
	conn, err := server.Accept()
	if err != nil {
		log.Printf("cannot accept connection: %v", err)
		continue
	}
	svcConn := connPool.Get() // 从池里拿，而不是现场 connectToService()
	fmt.Fprintln(conn, "")
	connPool.Put(svcConn)
	conn.Close()
}

每个请求现场建立连接1,000,385,643 ns/op（约 1 秒）

★ 使用 Pool 的四条规则
  • 实例化 sync.Pool 时，提供的 New 必须是并发安全的。
  • 从 Get 拿到的实例，不要对它的状态做任何假设（可能是新建的，也可能是别人用过的）。
  • 用完一定要 Put 回去，否则池就没用了。通常用 defer。
  • 池里的对象应该大致同质。如果需要长度随机变化的切片，拿到合适长度的概率很低，池帮不上什么忙，转换的开销可能比新建还大。
🆕 新版 Go：关于 Pool 的几点更新
  • Go 1.13+ 池里的对象不会在一次 GC 后全部丢失，而是先进入「受害者缓存」，要连续两次 GC 都没被用到才会被回收，GC 后的性能抖动小了很多。
  • 真正的连接池（数据库连接等）一般不用 sync.Pool：GC 可能随时清空它，而且它不负责关闭连接。database/sql 自带连接池，HTTP 客户端由 http.Transport 管理连接复用。sync.Pool 最适合 bytes.Buffer 这类临时缓冲区。
  • 书中用到的 ioutil.ReadAll 自 Go 1.16 起已弃用，请用 io.ReadAll。

通道（channel）

通道是 Go 从 Hoare 的 CSP 里继承来的同步原语。它可以用来同步内存访问，但最适合用来在 goroutine 之间传递信息。 通道可以组合，这让它在任何规模的程序里都非常有用。

像一条河一样，通道是信息流的管道：值沿着通道传递，在下游被读出。所以作者习惯给通道变量起名为 xxxStream。 程序的不同部分不需要了解彼此，只需要持有同一个通道的引用。

声明、方向和类型

var dataStream chan interface{}      // ① 声明一个通道，元素类型是空接口（可以放任何值）
dataStream = make(chan interface{})  // ② 用内建的 make 创建

通道也可以声明为单向的 —— 只能发送或只能接收。<- 写在 chan 左边是只读，写在右边是只写：

只能接收（只读）
var dataStream <-chan interface{}
dataStream := make(<-chan interface{})
只能发送（只写）
var dataStream chan<- interface{}
dataStream := make(chan<- interface{})

很少直接创建单向通道，但它们常用作函数参数和返回类型。Go 会在需要时把双向通道隐式转换为单向通道： 

var receiveChan <-chan interface{}
var sendChan chan<- interface{}
dataStream := make(chan interface{})

// 合法：双向 → 单向
receiveChan = dataStream
sendChan = dataStream

通道是有类型的。chan interface{} 可以放任何数据，但通常应该用更严格的类型，比如 intStream := make(chan int)。

发送、接收与阻塞

发送时 <- 在通道右边，接收时在通道左边。可以理解为：数据沿着箭头的方向流动。 

stringStream := make(chan string)
go func() {
	stringStream <- "Hello channels!" // ① 把字符串放进通道
}()
fmt.Println(<-stringStream) // ② 从通道读出并打印

往只读通道写、从只写通道读都是编译错误，这是 Go 类型系统给并发原语提供的类型安全： 

invalid operation: <-writeStream (receive from send-only type chan<- interface {})
invalid operation: readStream <- struct {} literal (send to receive-only type <-chan interface {})

还记得「goroutine 被调度了也不保证在进程退出前运行」吗？上面的例子却总是正确的，为什么？因为通道是阻塞的：

  • 往一个满的通道写，会等到通道有空位；
  • 从一个空的通道读，会等到至少有一个元素。

阻塞也意味着：结构写得不对就会死锁。下面用一个荒谬的条件阻止 goroutine 发送：

stringStream := make(chan string)
go func() {
	if 0 != 1 { // ① 保证永远不会往通道里放值
		return
	}
	stringStream <- "Hello channels!"
}()
fmt.Println(<-stringStream)

fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan receive]:
main.main()

主 goroutine 在等一个永远不会来的值；匿名 goroutine 退出后，Go 正确地检测到所有 goroutine 都睡着了，报告死锁。

关闭通道与 ok 习语

接收操作可以返回两个值：

stringStream := make(chan string)
go func() {
	stringStream <- "Hello channels!"
}()
salutation, ok := <-stringStream // ① 同时接收值和一个布尔值
fmt.Printf("(%v): %v", ok, salutation) // (true): Hello channels!

第二个返回值表示：这次读到的值是别处真正写入的，还是因为通道已关闭而产生的零值。 在程序里能表达「不会再有值发过来了」非常有用，下游可以据此继续、退出或换个通道。我们可以为每种类型约定一个哨兵值， 但这是通道的功能，不是数据类型的功能。关闭通道就像一个通用的哨兵，宣告「上游不会再写了」： 

intStream := make(chan int)
close(intStream)
integer, ok := <-intStream // ① 从已关闭的通道读
fmt.Printf("(%v): %v", ok, integer) // (false): 0

我们从没往通道里放过东西，但依然可以读，而且可以无限次地读，每次都立即得到零值和 false。这是为了支持「一个上游写者、多个下游读者」（第 4 章很常见）。

这带来了一个新模式：range 一个通道，通道关闭时循环自动结束：

intStream := make(chan int)
go func() {
	defer close(intStream) // ① 退出 goroutine 前一定关闭通道（非常常见的模式）
	for i := 1; i <= 5; i++ {
		intStream <- i
	}
}()

for integer := range intStream { // ② range 会在通道关闭时自动退出循环
	fmt.Printf("%v ", integer)
}
// 输出：1 2 3 4 5

关闭通道也是同时通知多个 goroutine 的方法之一：如果有 n 个 goroutine 在等同一个通道，不必写 n 次，关闭它就行。 因为已关闭的通道可以被无限次读取，有多少个等待者都无所谓，而且关闭比 n 次写入更便宜、更快： 

begin := make(chan interface{})
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
	wg.Add(1)
	go func(i int) {
		defer wg.Done()
		<-begin // ① 等待「可以开始了」的信号
		fmt.Printf("%v has begun\n", i)
	}(i)
}

fmt.Println("Unblocking goroutines...")
close(begin) // ② 关闭通道，同时放行所有 goroutine
wg.Wait()

前面讲过 sync.Cond 也能做到这一点。但通道可以组合，所以这是作者最喜欢的「同时放行多个 goroutine」的方式。

🆕 新版 Go：纯信号通道用 chan struct{}

书中大量使用 chan interface{} 作为「完成信号」通道。如今更地道的写法是 chan struct{}： 空结构体不占内存，类型本身就说明了「这个通道只传递信号、不传数据」。标准库的 ctx.Done() 返回的就是 <-chan struct{}。 另外 Go 1.18 起 interface{} 可以写成 any。

带缓冲的通道

创建通道时可以给一个容量，这就是带缓冲的通道：即使没有人读，goroutine 也能先写入 n 次（n 是容量）。 

var dataStream chan interface{}
dataStream = make(chan interface{}, 4) // ① 容量为 4：不管有没有人读，都能先放 4 个

有意思的是，带缓冲通道的声明和无缓冲通道毫无区别 —— 是创建通道的那个 goroutine 决定了它是否带缓冲。 这暗示着：通道的创建应该和执行写入的 goroutine 紧密耦合，这样才容易推理它的行为和性能。

其实无缓冲通道就是容量为 0 的带缓冲通道：make(chan int) 和 make(chan int, 0) 完全等价。 记得「写满了就阻塞、读空了就阻塞」吗？「满」和「空」是相对于容量说的：容量为 0 的通道在写入之前就已经「满」了。 容量为 4、没有读者的通道，写 4 次后变满，第 5 次写就会阻塞。所以带缓冲通道依然是阻塞的，只是条件不同 —— 它就是一个供并发进程通信用的内存 FIFO 队列。

⚠ 谨慎使用缓冲

带缓冲的通道在某些场景下有用，但要小心创建。下一章会看到，它很容易变成过早优化，还会掩盖死锁（让死锁变得不太容易发生）。 听起来像好事？你肯定更希望在第一次写代码时就发现死锁，而不是半夜生产系统宕机时。 

var stdoutBuff bytes.Buffer         // ① 内存缓冲区，减轻输出的不确定性（并不保证）
defer stdoutBuff.WriteTo(os.Stdout) // ② 进程退出前写到标准输出

intStream := make(chan int, 4) // ③ 容量为 4 的带缓冲通道

		fmt.Fprintf(&stdoutBuff, "Sending: %d\n", i)

	}
}()

可以看到匿名 goroutine 在主 goroutine 读出第一个值之前，就把 5 个结果全放进了通道并退出。 这是一种在合适条件下有用的优化：如果写者知道自己要写多少次，可以创建容量等于写入次数的通道，然后尽快写完。当然也有注意事项，下一章再说。

nil 通道

通道的零值是 nil。对 nil 通道做各种操作会怎样？

读 nil 通道

<-dataStream 永远阻塞（这里所有 goroutine 都阻塞了，所以报 deadlock）。

写 nil 通道

dataStream <- struct{}{} 同样永远阻塞。

关闭 nil 通道

close(dataStream) 直接 panic: close of nil channel。最糟的结果。

所以一定要确保你使用的通道已经初始化。（第 4 章会看到，「读 nil 通道永远阻塞」这个特性在 select 里反而很有用。）

通道所有权

第一件事是明确通道的所有权。作者把「所有者」定义为：创建、写入并关闭通道的那个 goroutine。 就像没有 GC 的语言里的内存一样，弄清楚谁拥有通道，才能对程序进行逻辑推理。单向通道就是区分所有者和使用者的工具： 所有者持有可写的视图（chan 或 chan<-），使用者只持有只读视图（<-chan）。

由所有者承担这些职责，会带来：

  • 通道是我们创建的 → 消除了写 nil 通道导致死锁、关闭 nil 通道导致 panic 的风险；
  • 何时关闭由我们决定 → 消除了写已关闭通道、重复关闭导致 panic 的风险；
  • 利用编译期的类型检查，防止别人错误地写我们的通道。

作为消费者，只需要操心两件事：知道通道什么时候关闭（检查第二个返回值）；负责任地处理阻塞 —— 想超时、想在被告知时停止，还是愿意一直阻塞，取决于你的算法。下一章会讲各种实现方式。

chanOwner := func() <-chan int {
	resultStream := make(chan int, 5) // ① 已知要产生 6 个结果，建一个容量为 5 的缓冲通道，让 goroutine 尽快完成
	go func() {                       // ② 启动匿名 goroutine 往 resultStream 写；注意 goroutine 被封装在函数内部了
		defer close(resultStream)     // ③ 作为所有者，用完一定关闭
		for i := 0; i <= 5; i++ {
			resultStream <- i
		}
	}()
	return resultStream // ④ 返回值声明为只读通道，自动转换
}

resultStream := chanOwner()
for result := range resultStream { // ⑤ 消费者只关心阻塞和关闭
	fmt.Printf("Received: %d\n", result)
}
fmt.Println("Done receiving!")

resultStream 的整个生命周期都封装在 chanOwner 里：写入显然不会发生在 nil 或已关闭的通道上，关闭也只会发生一次。 作者强烈建议让通道所有权的范围尽量小。如果一个结构体把通道作为字段、又有一堆方法，通道的行为很快就会变得难以判断。 你的程序也许依然会出现死锁或 panic，但出现时你多半会发现：要么所有权范围太大了，要么所有权变得不清楚了。

select 语句

如果说通道是把 goroutine 粘在一起的胶水，那 select 就是把通道粘在一起的胶水。 它让我们能在程序中组合通道，形成更大的抽象。说 select 是并发 Go 程序中最关键的东西之一，一点也不夸张。 它可以在一个函数或类型内部把通道绑在一起，也可以在系统中两个组件的交界处工作；还能把通道和取消、超时、等待、默认值等概念安全地结合起来。 

var c1, c2 <-chan interface{}
var c3 chan<- interface{}
select {
case <-c1:
	// 做点什么
case <-c2:
	// 做点什么
case c3 <- struct{}{}:
	// 做点什么
}

看起来像 switch，但相似之处仅此而已。和 switch 不同，select 的 case 不是按顺序测试的， 条件都不满足时也不会「落空」继续往下。所有通道的读写会被同时考虑，看哪个已经就绪：读的话，通道里有值或已关闭；写的话，通道还没满。 一个都没就绪，整个 select 就阻塞；有一个就绪了，就执行对应的操作和语句。 

start := time.Now()
c := make(chan interface{})
go func() {
	time.Sleep(5 * time.Second)
	close(c) // ① 5 秒后关闭通道
}()

fmt.Println("Blocking on read...")
select {
case <-c: // ② 尝试读。这里其实不需要 select，直接 <-c 也行，但我们会扩展这个例子
	fmt.Printf("Unblocked %v later.\n", time.Since(start))
}
// Blocking on read...
// Unblocked 5.000170047s later.

这是一种简单高效的「等某事发生」的方式。但仔细想想，会冒出几个问题：

  1. 多个通道都可读时会怎样？
  2. 如果没有任何通道会就绪呢？
  3. 如果没有通道就绪时，我们想先做点别的呢？

问题 1：多个通道同时就绪

c1 := make(chan interface{}); close(c1)
c2 := make(chan interface{}); close(c2)

var c1Count, c2Count int
for i := 1000; i >= 0; i-- {
	select {
	case <-c1:
		c1Count++
	case <-c2:
		c2Count++
	}
}
fmt.Printf("c1Count: %d\nc2Count: %d\n", c1Count, c2Count)
// c1Count: 505
// c2Count: 496

一千次里大约一半读了 c1，一半读了 c2。这不是巧合：Go 运行时会在就绪的 case 里做伪随机的均匀选择，每个 case 被选中的机会相等。 原因很有意思：运行时无法知道你把这组通道放进 select 的意图，它能做的最好的事就是在平均情况下表现良好。 引入随机变量、给每个通道相同的概率，所有用 select 的 Go 程序在平均情况下都会表现良好（也避免了某个通道被饿死）。

问题 2：永远没有通道就绪 —— 超时

var c <-chan int
select {
case <-c: // ① 读 nil 通道，永远不会就绪
case <-time.After(1 * time.Second):
	fmt.Println("Timed out.")
}

time.After 接受一个时长，返回一个通道，在那段时间之后往通道里发送当前时间。这为 select 提供了一种简洁的超时方式。 第 4 章会介绍更健壮的方案（context）。

🆕 新版 Go：定时器的两个变化 Go 1.23+
  • 在 Go 1.23 之前，在循环里反复调用 time.After 会让每个定时器一直存活到触发为止，高频循环里可能累积大量内存；类似地，time.Tick 创建的 Ticker 永远不会被回收。Go 1.23 起，不再被引用的 Timer/Ticker 即使没有 Stop 也能被 GC 回收，time.Tick 的文档也删除了「会泄漏」的警告。
  • 同样从 Go 1.23 起，定时器的通道变成了同步（无缓冲）的：Reset、Stop 之后保证不会再收到旧的过期值，不再需要以前那种「Stop 后清空通道」的繁琐写法。

在 Go 1.23–1.26 中，这两项变化只对 go.mod 声明 go 1.23 或更高的模块生效（可用 GODEBUG=asynctimerchan=1 退回）；Go 1.27 移除了这个开关，统一采用新行为。对于跨多个函数调用的超时，仍然推荐用 context.WithTimeout。

问题 3：没有就绪时做别的事 —— default

start := time.Now()
var c1, c2 <-chan int
select {
case <-c1:
case <-c2:
default:
	fmt.Printf("In default after %v\n\n", time.Since(start)) // In default after 1.421µs
}

default 几乎是立即执行的，这让你可以不阻塞地退出 select。它通常和 for-select 循环一起使用， 让 goroutine 在等待另一个 goroutine 报告结果的同时继续推进工作： 

done := make(chan interface{})
go func() {
	time.Sleep(5 * time.Second)
	close(done)
}()

workCounter := 0
loop:
for {
	select {
	case <-done:
		break loop // 用标签跳出外层 for（单写 break 只会跳出 select）
	default:
	}

	// 模拟工作
	workCounter++
	time.Sleep(1 * time.Second)
}

fmt.Printf("Achieved %v cycles of work before signalled to stop.\n", workCounter)
// Achieved 5 cycles of work before signalled to stop.

最后还有一个特殊情况：没有任何 case 的 select {}，它会永远阻塞。第 6 章会深入 select 的工作原理。

GOMAXPROCS 调节杆

runtime 包里有个函数叫 GOMAXPROCS。作者认为这个名字有误导性：人们常以为它和宿主机的逻辑处理器数有关（间接来说确实有）， 但它真正控制的是承载所谓「工作队列」的 OS 线程数量（第 6 章详解）。

Go 1.5 之前，GOMAXPROCS 默认是 1，几乎每个程序里都能看到 runtime.GOMAXPROCS(runtime.NumCPU())。 因为几乎所有人都想用满所有核，后来的版本把它默认设为宿主机的逻辑 CPU 数。

大多数时候你不需要调它。作者分享过一个例子：一个项目的测试套件被竞态条件困扰，测试机只有 4 个逻辑 CPU，同一时刻只有 4 个 goroutine 在执行。 他们把 GOMAXPROCS 调到超过 CPU 数，竞态被触发得更频繁，于是更快地修掉了它们。 如果你通过实验发现某个值让程序跑得更好，作者提醒：每次提交、换硬件、换 Go 版本都要重新验证。调这个值让程序更贴近硬件，代价是抽象和长期性能的稳定性。

🆕 新版 Go：GOMAXPROCS 会感知容器配额并自动更新 Go 1.25+

以前在 Docker/Kubernetes 里，runtime.NumCPU() 返回的是宿主机的核数，而容器可能只被分配了 2 个 CPU 的配额， 导致线程过多、频繁被限流，大家只好引入 go.uber.org/automaxprocs。Go 1.25 起，在 Linux 上 GOMAXPROCS 的默认值会综合 逻辑 CPU 数、CPU 亲和性掩码和 cgroup 的 CPU 配额，并且会在这些条件变化时周期性地自动更新。 手动设置 GOMAXPROCS 环境变量或调用 runtime.GOMAXPROCS(n) 会关闭自动更新；该行为由 go.mod 的 go 版本（≥1.25）控制，可用 GODEBUG=containermaxprocs=0 退回旧行为。 另外，想用不同并行度跑测试时，可以用 go test -cpu=1,2,4,8。

本章小结

构件一句话最适合
go f()启动一个并发运行的函数任何可以并发的工作单元，放心多开
sync.WaitGroup等待一组 goroutine 结束不关心结果、或结果另有渠道收集
sync.Mutex / RWMutex保护临界区结构体内部状态；读多写少用 RWMutex
sync.Cond等待 / 广播事件需要反复广播且性能敏感的场景（少见）
sync.Once只执行一次懒初始化；新代码优先 OnceFunc/OnceValue
sync.Pool复用临时对象高频分配的同质对象，如缓冲区
channel在 goroutine 间传递数据和所有权转移所有权、协调多段逻辑、组合
select同时等待多个通道操作超时、取消、非阻塞操作、组合通道
