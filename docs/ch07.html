工具箱：读 panic、找竞态、做剖析

写并发代码，离不开分析正确性的工具，也需要一些帮助你理解程序内部发生了什么的手段。Go 生态在这方面非常丰富。 原书附录介绍了三件事：goroutine panic 时的输出怎么读、竞态检测器、以及 pprof。本笔记在后半部分补充了书出版后出现的新工具。

本附录内容

  • 用 -race 找出数据竞争，并把它放进 CI
  • 用 runtime/pprof 观察 goroutine 数量、阻塞与锁争用

读懂 goroutine 的 panic

迟早有一天你的程序会 panic。运气好的话，没有人或机器受到伤害，最糟也就是盯着一份栈跟踪发呆。 在 Go 1.6 之前，goroutine panic 时运行时会打印所有正在运行的 goroutine 的栈，有时很难（至少很费时间）找出发生了什么。 Go 1.6 起只打印发生 panic 的那个 goroutine 的栈，简单多了。 

package main

func main() {
	waitForever := make(chan interface{})
	go func() {
		panic("test panic") // 第 6 行
	}() // 第 7 行
	<-waitForever
}

panic: test panic

goroutine 4 [running]:
main.main.func1()
	/tmp/babel-3271QbD/go-src-32713Rn.go:6 +0x65
created by main.main
	/tmp/babel-3271QbD/go-src-32713Rn.go:7 +0x4e
exit status 2

如果想看 panic 时所有正在执行的 goroutine 的栈，可以把环境变量 GOTRACEBACK 设为 all，恢复旧行为（还有 system、crash 等级别，会显示更多运行时内部信息）。

🆕 新版 Go：栈跟踪里能看到「父 goroutine」了 Go 1.21+

同样的程序在 Go 1.27 上输出：

panic: test panic

goroutine 18 [running]:
main.main.func1()
	/.../panic/main.go:6 +0x25
created by main.main in goroutine 1
	/.../panic/main.go:5 +0x2d

「created by ... in goroutine 1」告诉你是哪个 goroutine 启动了它，排查「谁创建了这些泄漏的 goroutine」时非常有用。 另外 Go 1.26 加入、Go 1.27 默认开启的 tracebacklabels，会把通过 pprof.Do 设置的 goroutine 标签显示在栈跟踪的头部， 例如标上请求 ID，就能知道崩溃的 goroutine 在处理哪个请求。

竞态检测（Race Detection）

Go 1.1 给大多数 go 命令加入了 -race 标志：

$ go test -race mypkg    # 测试这个包
$ go run -race mysrc.go  # 编译并运行程序
$ go build -race mycmd   # 构建命令
$ go install -race mypkg # 安装包

如果你只需要一种更可靠的检测竞态条件的方法，知道这些就够了。一个需要注意的地方是：它只能发现「实际被执行到」的代码里的竞态。 所以 Go 团队建议在真实负载下运行用 -race 构建的程序 —— 执行到的代码越多，发现竞态的概率越大。

第 1 章那个简单的程序：

var data int
go func() {
	data++
}()
if data == 0 {
	fmt.Printf("the value is %v.\n", data)
}

==================
WARNING: DATA RACE
Write at 0x00c000096028 by goroutine 8:
  main.main.func1()
      /.../race/main.go:8 +0x44

Previous read at 0x00c000096028 by main goroutine:
  main.main()
      /.../race/main.go:10 +0xae

Goroutine 8 (running) created at:
  main.main()
      /.../race/main.go:7 +0xa4
==================
Found 1 data race(s)
exit status 66

竞态检测器还有一些可以通过环境变量调整的选项，不过默认值通常就够了。注意它们都写在 GORACE 环境变量里，如 GORACE="log_path=/tmp/race strip_path_prefix=/my/src/"：

log_path
把报告写到 log_path.pid 文件。也可以用特殊值 stdout、stderr，默认是 stderr。
strip_path_prefix
去掉报告里文件路径的前缀，让报告更简洁。
history_size
每个 goroutine 记住多少次之前的内存访问，取值 0–7。内存从 32KB（0）开始每级翻倍，最大 4MB（7）。报告里看到「failed to restore the stack」时就该调大它，但会显著增加内存消耗。
halt_on_error
发现第一个竞态就退出（书中未提及，调试时很有用）。
★ 把竞态检测放进持续集成

作者强烈建议把它集成进 CI。再强调一次：它只能检测实际发生的竞态，而竞态有时很难触发，所以应该持续地运行真实场景来尝试触发。 代价是程序会慢很多（通常内存增加 5–10 倍、执行时间增加 2–20 倍），所以一般不在生产环境长期开启。

pprof

在大型代码库里，很难弄清程序运行时的表现：有多少 goroutine 在跑？CPU 用满了吗？内存怎么样？性能剖析（profiling）是回答这些问题的好办法。 Go 标准库里支持一个叫 pprof 的剖析器（源自 Google），它既能在程序运行时显示剖析数据，也能读取保存下来的运行时统计。 它的命令行用法 go tool pprof -h 说得很清楚，这里只讨论和并发相关的 runtime/pprof 包。它预定义了这些剖析：

剖析名内容并发相关的用途
goroutine当前所有 goroutine 的栈发现 goroutine 泄漏、看大家都卡在哪
heap堆上存活对象的分配采样内存为何增长
allocs所有历史分配的采样（书出版后加入）找分配热点
threadcreate导致创建新 OS 线程的栈为什么线程数这么多（常见于阻塞的系统调用、cgo）
block在同步原语上阻塞的栈谁在等通道、等锁、等 select（需先 runtime.SetBlockProfileRate）
mutex争用激烈的互斥锁的持有者锁竞争（需先 runtime.SetMutexProfileFraction）
goroutineleak已泄漏的 goroutine 的栈Go 1.26 实验 / 1.27 见下一节

比如，下面这个 goroutine 每秒记录一次当前 goroutine 的数量，可以帮你发现泄漏：

log.SetFlags(log.Ltime | log.LUTC)
log.SetOutput(os.Stdout)

// 每秒记录一次当前运行的 goroutine 数量
go func() {
	goroutines := pprof.Lookup("goroutine")
	for range time.Tick(1 * time.Second) {
		log.Printf("goroutine count: %d\n", goroutines.Count())
	}
}()

// 创建一些永远不会退出的 goroutine
var blockForever chan struct{}
for i := 0; i < 10; i++ {
	go func() { <-blockForever }()
	time.Sleep(500 * time.Millisecond)
}

内置剖析已经很有用，你还可以写自定义的剖析来监控程序：

func newProfIfNotDef(name string) *pprof.Profile {
	prof := pprof.Lookup(name)
	if prof == nil {
		prof = pprof.NewProfile(name)
	}
	return prof
}

prof := newProfIfNotDef("my_package_namespace")
// prof.Add(resource, 1) 记录「谁持有了这个资源」，prof.Remove(resource) 在释放时移除
// 适合追踪必须显式关闭的资源，如文件、连接
🆕 新版 Go：更方便的 pprof 用法
  • 服务程序里加一行 import _ "net/http/pprof"，就能通过 /debug/pprof/ 下载实时剖析，例如：go tool pprof -http=:8080 http://localhost:6060/debug/pprof/goroutine，在浏览器里看火焰图。
  • 测试时：go test -cpuprofile cpu.out -memprofile mem.out -blockprofile block.out -mutexprofile mutex.out。
  • runtime.NumGoroutine() 是最简单的 goroutine 计数；runtime/metrics（Go 1.16+）提供了稳定的运行时指标接口，如 /sched/goroutines:goroutines、/sync/mutex/wait/total:seconds，适合接入监控系统。
  • pprof.Do(ctx, pprof.Labels("request", id), f) 可以给 goroutine 打标签，在 CPU 和 goroutine 剖析里按标签过滤。

新工具：goroutine 泄漏剖析 Go 1.26 实验 / 1.27

第 4 章说过「goroutine 不会被垃圾回收」。新版运行时在这一点上前进了一步：垃圾回收器本来就知道哪些对象「不可达」， 如果一个 goroutine 阻塞在一个除了它自己以外再也没人能访问到的通道或锁上，那它就永远不可能被唤醒 —— 这就是泄漏。 goroutineleak 剖析会触发一次带泄漏检测的 GC，只报告这类 goroutine。它在 Go 1.26 以实验形式出现（需要 GOEXPERIMENT=goroutineleakprofile），在 Go 1.27 中默认可用。 

func main() {
	for i := 0; i < 3; i++ {
		ch := make(chan int)
		go func() { <-ch }() // 泄漏：除了这个 goroutine，没人再引用 ch
	}
	time.Sleep(100 * time.Millisecond)

	pprof.Lookup("goroutineleak").WriteTo(os.Stdout, 1)
}

goroutineleak profile: total 3
3 @ 0x47d82a 0x41512e 0x414c72 0x4deaf9 0x483561
#	0x4deaf8	main.main.func1+0x18	/.../leak.go:13

注意它只能发现「阻塞在不可达同步原语上」的泄漏。如果泄漏的 goroutine 阻塞在一个全局变量引用的通道上，或者在死循环里空转，它就无能为力。测试里还可以用：

  • go.uber.org/goleak：defer goleak.VerifyNone(t) 或在 TestMain 里 goleak.VerifyTestMain(m)，测试结束时如果还有多余的 goroutine 就失败；
  • testing/synctest（见下文）：气泡结束时若仍有阻塞的 goroutine，测试失败。

新工具：testing/synctest Go 1.25+

第 5 章花了很多篇幅对付「并发测试里时间不确定」的问题。testing/synctest 给出了标准答案：在一个隔离的「气泡（bubble）」里运行测试， 气泡里的 goroutine 使用假时钟（从 2000-01-01 00:00 UTC 开始），只有当气泡里所有 goroutine 都「持久阻塞」时，时间才会前进到下一个定时事件。 

func TestTimeout(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		ctx, cancel := context.WithTimeout(t.Context(), 5*time.Second)
		defer cancel()

		time.Sleep(4 * time.Second) // 瞬间完成
		synctest.Wait()             // 等气泡里其他 goroutine 都阻塞下来
		if err := ctx.Err(); err != nil {
			t.Fatalf("还没到 5 秒就超时了: %v", err)
		}

		time.Sleep(time.Second)
		synctest.Wait()
		if ctx.Err() != context.DeadlineExceeded {
			t.Fatal("5 秒后应该超时")
		}
	})
}
✓ synctest 的几条使用建议
  • 测试要自包含：不要和气泡外启动的 goroutine 交互，避免真实网络（用 net.Pipe 等内存实现），避免外部进程。
  • 「持久阻塞」指阻塞在气泡内的通道、select、sync.WaitGroup、sync.Cond、time.Sleep 等上；阻塞在系统调用或气泡外的锁上不算。
  • 它让「超时」「心跳」「限流」「重试退避」这些和时间有关的逻辑都能被快速、确定地测试。

新工具：执行追踪与飞行记录器

pprof 告诉你「在哪里花了时间」，执行追踪（execution trace）告诉你「什么时候发生了什么」：每个 P 上 goroutine 什么时候运行、为什么阻塞、被谁唤醒、GC 何时发生。它特别适合排查延迟毛刺和并发度不足。 

$ go test -trace=trace.out ./...          # 测试时采集
$ go tool trace trace.out                 # 在浏览器里查看时间线
$ curl -o trace.out 'http://localhost:6060/debug/pprof/trace?seconds=5'  # 从运行中的服务采集
🆕 新版 Go：低开销追踪与飞行记录器 Go 1.22+Go 1.25+

Go 1.22 重写了追踪器，开销从 10–20% 降到 1–2% 左右，长时间开启也可以接受。Go 1.25 加入了 runtime/trace.FlightRecorder： 在内存里循环保存最近几秒的追踪数据，平时几乎不占资源，等程序检测到异常（比如某个请求特别慢）时，再把「事故发生前的那几秒」写到文件里 —— 就像飞机的黑匣子。 

fr := trace.NewFlightRecorder(trace.FlightRecorderConfig{
	MinAge:   5 * time.Second, // 至少保留最近 5 秒
	MaxBytes: 16 << 20,
})
fr.Start()
defer fr.Stop()

// ……某个请求处理得特别慢时：
if elapsed > 300*time.Millisecond {
	f, _ := os.Create("slow.trace")
	fr.WriteTo(f) // 导出事故前后的执行轨迹
	f.Close()
}

还可以用 GODEBUG=schedtrace=1000,scheddetail=1 每秒打印调度器状态（第 6 章）。
