第 2 章

用 CSP 为代码建模

这一章讲的是 Go 的「设计动机」。理解了它，你就能明白 Go 社区里那些口号 —— 「不要通过共享内存来通信，而要通过通信来共享内存」—— 到底在说什么， 以及什么时候该用通道、什么时候该老老实实用锁。

本章目标

  • 彻底分清「并发」和「并行」：一个是代码的属性，一个是运行的属性
  • 理解「上下文」决定正确性，以及为什么越往底层并发越难
  • 知道 CSP（通信顺序进程）是什么，它和 Go 的通道、select 有什么关系
  • 掌握「用锁还是用通道」的决策树

并发和并行的区别

很多人把这两个词混着用，意思都是「同时运行的东西」。区分它们不是咬文嚼字 —— 这个区分是一个非常强大的建模抽象，而 Go 充分利用了它。先记住这句话：

★ 并发是代码的属性；并行是运行中程序的属性。

Concurrency is a property of the code; parallelism is a property of the running program.

假设我写了一段代码，希望其中两块「并行」运行。如果把程序放到只有一个核的机器上呢？ 它们看起来在并行，其实是 CPU 在不同任务之间快速切换（上下文切换），在足够粗的时间粒度上看，就像同时在跑。 同一个二进制放到双核机器上，它们才可能真正并行。

这揭示了三件有趣的事：

  1. 我们从不写「并行代码」，只写「希望能被并行执行的并发代码」。并行是运行时的属性。
  2. 我们可以（甚至应该）不关心并发代码是否真的在并行。这要归功于程序下面的一层层抽象：并发原语、运行时、操作系统、虚拟机/容器、CPU。
  3. 并行与否取决于「上下文」（时间窗口或边界）。如果上下文是 5 秒，两个各跑 1 秒的操作可以算并行；如果上下文是 1 秒，它们就是顺序的。

第一章讲原子性时，「上下文」是判断一个操作是否原子的边界；这里它是判断两个操作是否并行的边界。 上下文不只能是时间，也可以是进程、操作系统线程、或者机器。而你选择的上下文，和「并发代码是否正确」密切相关。

上下文越往下，越难推理

举个例子：你我各自在自己电脑上打开计算器做加法，我的计算不会影响你的。这里机器是上下文，进程是并发操作。 我们用「独立的计算机、操作系统、进程」来建模，所以能很自信地断言正确性。

往下走一层：同一台机器上的两个进程呢？进程 A 可能覆盖进程 B 正在读的文件；在不安全的系统上，甚至可能破坏 B 的内存（很多漏洞就是这么来的）。 不过在进程层面，操作系统还能帮我们保持逻辑隔离。

再往下到操作系统线程这一层，第 1 章的所有问题都来了：竞态、死锁、活锁、饥饿。如果所有用户共享同一个计算器进程，要写对就难多了。

越往抽象栈下面走，并发建模越难推理，也越重要；反过来，我们的抽象也越重要。 不幸的是，业界大多数并发逻辑都写在了最高的一层：操作系统线程。 在 Go 出现之前，主流语言的抽象链到线程就结束了：想写并发，就用线程建模，再同步线程之间对内存的访问；线程太多，就建线程池，把操作复用到池子上。

Go 在这条链上加了一环：goroutine，还从 Tony Hoare 那里借来了通道（channel）。 按理说再往下加一层抽象会更难，但事实恰恰相反 —— 因为 Go 并没有在线程之上再叠一层，而是取代了线程。 线程当然还在，但我们很少需要按线程来思考问题，而是用 goroutine 和通道来建模，偶尔使用共享内存。

CSP 是什么？

谈到 Go 你经常会听到 CSP 这个缩写，有时它被吹成 Go 成功的原因、并发编程的灵丹妙药。CSP 确实让事情变简单、程序更健壮，但它不是奇迹。

CSP 是 Communicating Sequential Processes（通信顺序进程） 的缩写，既是一种技术，也是 1978 年 Tony Hoare （Charles Antony Richard Hoare）在 ACM 上发表的论文名。当时大家的精力都花在顺序程序的结构上：goto 该不该用、面向对象刚开始流行。 Hoare 认为，输入和输出是被忽视的两个编程原语，尤其是在并发代码里。

在 Hoare 的 CSP 语言里，「进程」指任何一段需要输入才能运行、并产生输出供其他进程消费的封装逻辑（如果不是当时编程界正在争论程序结构，他大概会直接叫它「函数」）。 进程之间用两个命令通信：! 表示发送，? 表示接收。

CSP 写法含义今天的 Go 大致对应
cardreader?cardimage从 cardreader 读一张卡片，赋给变量 cardimagecardimage := <-cardreader
lineprinter!lineimage把 lineimage 发给 lineprinter 打印lineprinter <- lineimage
X?(x, y)从名为 X 的进程读一对值，赋给 x 和 yp := <-X; x, y := p.x, p.y
DIV!(3*a+b, 13)向进程 DIV 输出两个值DIV <- pair{3*a+b, 13}
*[c:character; west?c → east!c]把 west 输出的字符逐个转发给 east；west 结束时循环结束for c := range west { east <- c }

和 Go 通道的相似之处一目了然。Hoare 最初的论文里，进程只能通过具名的源和目标通信，他也承认这会让代码难以做成库（调用者得知道输入输出的名字）， 并顺带提到可以注册「端口名」—— 我们今天大概会称之为具名参数和具名返回值。

CSP 还使用了 Dijkstra 在 1974 年提出的守卫命令（guarded command）：用 → 分隔的左右两部分， 左边是条件（守卫），只有守卫为真时右边才会执行。把守卫命令和 I/O 命令结合起来，就是 Hoare 的通信进程 —— 也是 Go 通道和 select 的基础。

历史证明 Hoare 是对的。但有意思的是，Go 之前很少有主流语言真正把这些原语放进语言里，大多数语言更偏爱共享内存加同步的方式。 Go 是最早把 CSP 原则放进核心、并带给大众的语言之一，它的成功也促使其他语言尝试加入类似原语。

ⓘ 共享内存并不「邪恶」

内存访问同步本身不坏，后面会看到某些场景下（即使在 Go 里）共享内存才是对的。只是共享内存模型很难用对，尤其在大型复杂程序里。 Go 从一开始就按 CSP 原则设计，因此并发代码更容易读、写和推理。

这对你有什么帮助

如果要类比，可以把 goroutine 比作线程、把通道比作互斥锁（二者只是「有点像」，这个类比只是帮你找到方向）。 这些不同的抽象带来了什么？

goroutine 让你不必用「并行」的方式思考问题，而是可以贴近问题本来的并发结构来建模。 比如要写一个 Web 服务器处理某个接口的请求。在只有线程抽象的语言里，你多半会纠结：

只有线程时，你在想……
  • 语言原生支持线程吗？还是要选个库？
  • 线程隔离（confinement）的边界划在哪？
  • 这个操作系统上线程有多重？
  • 不同操作系统处理线程有什么区别？
  • 要建个 worker 池限制线程数，最优数量是多少？
用 goroutine 时，你在想……
  • 每个用户连上来、开一个会话；
  • 会话处理请求、返回响应；
  • → 每个连接一个 goroutine，处理完就返回。
  • （问题自然的样子，直接映射成代码）

左边的问题都很重要，但没有一个和你要解决的问题直接相关 —— 你一下子被拽进了「怎样实现并行」的技术细节里。 这一切之所以可行，是因为 Go 向我们承诺：goroutine 是轻量的，通常不需要担心创建它们的成本。 系统里跑了多少 goroutine 有时确实值得关心，但一开始就考虑这个，属于过早优化；而对线程，你最好一开始就考虑。

「某些语言也有框架帮你屏蔽并行的细节」并不意味着这种自然的建模方式不重要：框架总得有人写，你的代码就坐在作者处理过的那堆复杂性上面。 复杂性被藏起来不代表它不存在，而复杂性滋生 bug。Go 语言本身是围绕并发设计的，原语和语言浑然一体，摩擦更少、bug 更少。

这种更自然的映射还带来几个附带好处：

⚙

关注点分离

运行时负责把 goroutine 复用到线程、负责调度。运行时变快了，你的程序不用改就跟着变快，比如 Go 1.5 修改了 goroutine 的调度顺序。

👀

运行时能「看见」阻塞

goroutine 在等 I/O 时，运行时能察觉并把线程让给其他未阻塞的 goroutine（第 6 章详解）。

📈

更细的并发粒度

每个用户一个 goroutine，而不是把连接复用到线程池上。粒度越细，程序越能随宿主机的并行能力动态伸缩 —— 阿姆达尔定律在起作用。

🧩

通道天生可组合

可以把多个子系统的输出组合起来，结合超时、取消、给其他子系统发消息。协调一堆互斥锁则困难得多。

select 语句是通道的好搭档，让组合通道的难点迎刃而解：它可以高效地等待事件、在多个就绪的通道中均匀随机地选一个、没有消息就继续往下走……

🆕 新版 Go：「白送」的运行时改进确实一直在来

书中说「关注 Go 的发布说明，运行时会在你不改代码的情况下让程序更快」。此后的几个例子： Go 1.14 引入异步抢占，没有函数调用的死循环也不会再霸占线程（第 6 章）； Go 1.25 起 GOMAXPROCS 默认会感知容器的 CPU 配额，在 Kubernetes 里不再需要第三方库 automaxprocs； Go 1.26 默认启用新的 Green Tea 垃圾回收器。这些都只需要升级 Go 版本、重新编译。

Go 的并发哲学

CSP 是 Go 设计的核心，但 Go 同样支持传统的内存访问同步：sync 等包里的结构体和方法可以加锁、建资源池、抢占 goroutine 等等。 能二选一是好事，但也会让人困惑。新手常以为 CSP 风格是 Go 里写并发的唯一正确方式，比如 sync 包文档写道：

sync 包提供基本的同步原语，如互斥锁。除了 Once 和 WaitGroup 类型，大多数是给底层库例程用的。更高层的同步最好通过通道和通信来完成。

Go 的 FAQ 里写着：

关于互斥锁，sync 包实现了它们，但我们希望 Go 的编程风格能鼓励大家尝试更高层的技术。特别是，考虑把程序组织成：同一时刻只有一个 goroutine 负责某一份数据。
不要通过共享内存来通信；而要通过通信来共享内存。

可你在实际代码里又经常看到互斥锁，也会听到有人抱怨通道被滥用，Go 团队成员也说用锁没问题。Go Wiki 的说法是：

Go 的格言之一是「通过通信共享内存，而不是通过共享内存通信」。尽管如此，Go 在 sync 包里也提供了传统的锁机制。大多数加锁问题用通道或传统锁都能解决。
那么该用哪个？用最有表现力和/或最简单的那个。

好建议，但有点模糊。怎么判断哪个「更有表现力、更简单」？关键在于：你管理并发的范围是在一个很小的作用域内部，还是贯穿整个系统。 作者把判断依据整理成了一棵决策树：

② 你是在转移数据的所有权吗？

如果一段代码产生了结果，想交给另一段代码，你实际上是在转移这份数据的所有权。 熟悉没有垃圾回收的语言的人会懂：数据有一个主人，让并发程序安全的一种办法就是保证同一时刻只有一个并发上下文拥有这份数据。 通道把这种意图编码进了通道的类型里。

  • 可以用带缓冲的通道实现一个廉价的内存队列，让生产者和消费者解耦；
  • 用了通道，你的并发代码就天然能和其他并发代码组合。

③ 你在保护结构体的内部状态吗？

这正是内存访问同步原语的用武之地，也是一个很强的「不要用通道」的信号。用锁可以把「加锁」这个实现细节对调用者隐藏起来。 下面是一个线程安全、却不向调用者暴露复杂性的小类型： 

type Counter struct {
	mu    sync.Mutex
	value int
}

func (c *Counter) Increment() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}

回忆原子性的概念：我们在这里为 Counter 类型定义了原子性的范围 —— 对 Increment 的调用可以视为原子的。 关键词是内部：如果你发现自己把锁暴露到了类型之外，就该亮红灯了。尽量把锁限制在很小的词法作用域里。

④ 你在协调多段逻辑吗？

通道天生比内存同步原语更容易组合。锁散落在整个对象图里听起来像噩梦，但到处都是通道却是正常、被鼓励的！ 你可以组合通道，却很难组合锁或「返回值的方法」。 有了 select，加上通道可以当队列用、可以安全地到处传递，你会发现用通道更容易控制软件里涌现出来的复杂性。 如果你在用原语，却搞不清并发代码是怎么运行的、为什么死锁或出现竞态，这多半意味着你该换成通道了。

① 这是性能关键的代码段吗？

这绝不是说「我想要程序快，所以只用互斥锁」。它的意思是：如果你经过性能剖析发现某段代码是主要瓶颈、比其他部分慢好几个数量级， 那么用内存同步原语可能有助于它在负载下的表现 —— 因为通道内部本身就用了内存同步，所以只可能更慢。 不过在考虑这个之前，一个性能关键段也可能在暗示：程序结构需要调整。

✓ 忘掉线程时代的「池化」习惯

在以线程为抽象的语言里，线程池之类的模式很常见。它们大多是为了扬长避短地使用线程而存在的。 在 Go 里一个好的经验法则是：丢掉这些模式。它们并非完全没用，但在 Go 里适用面窄得多。 用 goroutine 表示工作流中的并发部分，大胆地启动它们。你更可能需要重构程序，而不是先撞上硬件能支持的 goroutine 数量上限。

🆕 新版 Go：需要「限制并发数」时怎么写

不预先建 goroutine 池，不等于并发数永远不设上限 —— 比如同时发起的 HTTP 请求、打开的文件数。今天常见的做法是： 用 golang.org/x/sync/errgroup 的 g.SetLimit(n)，或者用一个容量为 n 的带缓冲通道当信号量，按需启动 goroutine 但限制同时运行的数量。 这仍然是「每个任务一个 goroutine」的思路，而不是「固定 n 个 worker 循环取任务」。 

var g errgroup.Group
g.SetLimit(8) // 最多 8 个同时运行，第 9 个 g.Go 会阻塞等待
for _, url := range urls {
	g.Go(func() error { return fetch(url) }) // Go 1.22+ 循环变量每轮独立，可直接引用
}
if err := g.Wait(); err != nil { // 返回第一个非 nil 错误
	log.Fatal(err)
}
★ 一句话概括 Go 的并发哲学

追求简单；能用通道就用通道；把 goroutine 当作免费资源。
