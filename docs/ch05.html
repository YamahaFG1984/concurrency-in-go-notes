第 5 章

大规模并发

学会了模式，接下来把模式再组合成「模式的模式」，用来构建大型、可组合、能扩展的系统。 这一章讨论在单个进程内扩展并发操作的方法，也开始涉及多个进程之间的并发： 错误该长什么样、怎样超时和取消、怎样知道一个 goroutine 还活着、怎样限流、以及怎样让卡死的 goroutine 自动重启。

本章目标

  • 建立一套错误传播的框架：区分「bug」和「已知的边界情况」，在模块边界包装错误
  • 知道何时该超时、何时会被取消，以及如何让长时间运行的代码可被抢占
  • 用心跳监控 goroutine 的健康，并写出确定性的并发测试
  • 理解复制请求的取舍
  • 理解令牌桶限流算法，并用 golang.org/x/time/rate 组合多级限流
  • 用「管家（steward）—被监护者（ward）」模式自动治愈不健康的 goroutine

错误传播

在并发代码里，尤其是分布式系统里，出错很容易，搞清楚为什么出错却很难。仔细考虑问题怎样在系统中传播、最终怎样呈现给用户， 能为你、团队和用户省去大量痛苦。第 4 章「错误处理」讨论了怎样从 goroutine 里把错误传出来，但没讨论错误应该长什么样、 在大而复杂的系统里应该怎样流动。下面是作者一套有主见的框架。

很多开发者把错误传播当成「次要的」：精心设计数据怎样流动，错误却只是被容忍、被不假思索地沿栈往上扔，最后甩在用户面前。 Go 强制你在每一层处理错误，就是想纠正这个坏习惯。只要稍加思考，错误处理可以成为系统的资产，甚至让用户感到愉快。

一个错误应该包含什么

错误表示系统进入了一个无法完成用户（显式或隐式）请求的操作的状态。它需要传达几条关键信息：

❓

发生了什么

比如「磁盘已满」「套接字已关闭」「凭证已过期」。通常由产生错误的东西隐式生成，你可以加上有助于用户理解的上下文。

📍

何时何地发生

完整的栈跟踪（不要放在错误消息里，但要能取到）；运行的上下文，比如分布式系统里是哪台机器；以及错误创建时机器上的 UTC 时间。

🙂

友好的用户消息

针对你的系统和用户定制，只包含前两项中精简、相关的信息；以人为中心，说明问题是否是暂时的；最好只有一行。

🔍

怎样获取更多信息

给用户一个 ID，可以对照日志查看完整信息：错误发生（而非记录）的时间、栈跟踪……附上栈跟踪的哈希值还有助于在 bug 跟踪系统里归并同类问题。

默认情况下，没有任何错误会自动包含这些信息。所以可以这样认为：任何没有这些信息就传到用户面前的错误，都是错误 —— 也就是 bug。 于是所有错误可以分成两类：

  • Bug：没有针对你的系统定制过的「原始」错误；
  • 已知的边界情况：比如网络连接断开、磁盘写入失败，并且已经被包装成了格式良好的错误。

有时你会有意让边界情况的原始错误先暴露给用户，以便快速发布前几个版本；有时则是疏忽。但按这个思路，原始错误永远是 bug。 这个区分在决定怎样传播错误、系统怎样演进、最终给用户展示什么时都很有用。

在模块边界包装错误

设想一个有多个模块的大系统：

假设「底层组件」里发生了错误，我们在那里构造了一个格式良好的错误往上传。在底层组件的上下文里它是格式良好的，但在整个系统的上下文里未必。 我们规定：在每个组件的边界，所有传入的错误都必须被包装成本组件的格式良好的错误。比如在「中间组件」里调用底层组件： 

func PostReport(id string) error {
	result, err := lowlevel.DoWork()
	if err != nil {
		if _, ok := err.(lowlevel.Error); ok { // ① 确认收到的是格式良好的错误；如果不是，就原样往上传，以表明这是个 bug
			err = WrapErr(err, "cannot post report with id %q", id) // ② 用本模块的信息包装，并赋予新类型；可能会隐藏一些对用户无关紧要的底层细节
		}
		return err
	}
	// ...
}

错误根源的底层细节（哪个 goroutine、哪台机器、栈跟踪……）仍然在错误最初创建时就填好了，但我们的架构规定：在模块边界，把错误转换成本模块的错误类型。 现在，任何没有本模块错误类型就逃出本模块的错误，都可以被视为格式不良，也就是 bug。 注意只需要在自己的模块边界（公共函数/方法）或能补充有价值上下文时包装，大部分代码不需要这么做。

这让系统能够有机地成长：我们可以确信传入的错误格式良好，也会认真考虑错误怎样逃出自己的模块。「错误正确性」成了系统的一种涌现属性。 我们一开始就承认不完美，明确地处理格式不良的错误，由此获得了一个随时间发现并纠正错误的框架。

展示给用户时，这个区分就派上用场了：

  • 收到格式良好的错误：可以确信每一层都认真构造了消息，直接记日志、展示给用户即可；
  • 收到格式不良的错误（bug）：也要记日志，但给用户展示一条友好的「发生了意外」的消息；如果支持自动错误上报，就当作 bug 报告；否则建议用户提交 bug。

无论哪种情况，消息里都要带一个日志 ID，好奇的用户可以据此查看完整信息。

完整示例

先定义一个能容纳格式良好错误所有要素的类型：

type MyError struct {
	Inner      error                  // ① 被包装的错误：我们总想能回溯到最底层的错误
	Message    string
	StackTrace string                 // ② 错误创建时的栈跟踪
	Misc       map[string]interface{} // ③ 杂项：并发 ID、栈跟踪的哈希、其他有助于诊断的上下文
}

func wrapError(err error, messagef string, msgArgs ...interface{}) MyError {
	return MyError{
		Inner:      err,
		Message:    fmt.Sprintf(messagef, msgArgs...),
		StackTrace: string(debug.Stack()),
		Misc:       make(map[string]interface{}),
	}
}

func (err MyError) Error() string {
	return err.Message
}

// "lowlevel" 模块

type LowLevelErr struct {
	error
}

func isGloballyExec(path string) (bool, error) {
	info, err := os.Stat(path)
	if err != nil {
		return false, LowLevelErr{(wrapError(err, err.Error()))} // ① 包装 os.Stat 的原始错误；这里沿用原消息，不打算隐藏
	}
	return info.Mode().Perm()&0100 == 0100, nil
}

// "intermediate" 模块

type IntermediateErr struct {
	error
}

func runJob(id string) error {
	const jobBinPath = "/bad/job/binary"
	isExecutable, err := isGloballyExec(jobBinPath)
	if err != nil {
		return err // ① 直接把 lowlevel 的错误传出去了 —— 按我们的约定，这是个 bug
	} else if isExecutable == false {
		return wrapError(nil, "job binary is not executable")
	}

	return exec.Command(jobBinPath, "--id="+id).Run()
}

func handleError(key int, err error, message string) {
	log.SetPrefix(fmt.Sprintf("[logID: %v]: ", key))
	log.Printf("%#v", err) // ③ 把完整的错误记进日志，供需要时深挖
	fmt.Printf("[%v] %v", key, message)
}

func main() {
	log.SetOutput(os.Stdout)
	log.SetFlags(log.Ltime | log.LUTC)

	err := runJob("1")
	if err != nil {
		msg := "There was an unexpected issue; please report this as a bug."
		if _, ok := err.(IntermediateErr); ok { // ① 是期望的类型，说明是精心构造的错误，直接把消息给用户
			msg = err.Error()
		}
		handleError(1, err, msg) // ② 用 ID 1 把日志和错误消息绑在一起（实际可以递增或用 GUID）
	}
}

[logID: 1]: 21:46:07 main.LowLevelErr{error:main.MyError{Inner:(*os.PathError)(0xc4200123f0),
Message:"stat /bad/job/binary: no such file or directory", StackTrace:"goroutine 1 [running]: ..."}}

[1] There was an unexpected issue; please report this as a bug.

错误在传播路径上某处没被正确处理，我们无法确定它的消息适合给人看，所以只打印「发生了意外」。回头看 intermediate 模块就知道原因：没有包装 lowlevel 的错误。修正它： 

func runJob(id string) error {
	const jobBinPath = "/bad/job/binary"
	isExecutable, err := isGloballyExec(jobBinPath)
	if err != nil {
		return IntermediateErr{wrapError( // ① 用精心构造的消息定制错误；这里故意隐藏了底层细节，因为对本模块的调用者不重要
			err,
			"cannot run job %q: requisite binaries not available",
			id,
		)}
	} else if isExecutable == false {
		return wrapError(
			nil,
			"cannot run job %q: requisite binaries are not executable",
			id,
		)
	}

	return exec.Command(jobBinPath, "--id="+id).Run()
}

[1] cannot run job "1": requisite binaries not available

这个技巧是渐进式的：你可以先在顶层错误处理处区分 bug 和精心构造的错误，然后逐步确保自己创建的所有错误都是精心构造的。 书中推荐了当时流行的 github.com/pkg/errors 包来实现。

🆕 新版 Go：标准库的错误包装 Go 1.13+Go 1.20+Go 1.26+

书中依赖第三方包和类型断言。Go 1.13 起，标准库提供了错误包装：fmt.Errorf("...: %w", err) 包装、errors.Unwrap 解包、 errors.Is 比较哨兵错误、errors.As 沿着包装链查找某种类型。github.com/pkg/errors 已归档，不再推荐。 关键区别：类型断言 err.(IntermediateErr) 只检查最外层，一旦别人用 %w 再包一层就失效；errors.As 会遍历整条链。 

type MyError struct {
	Inner      error
	Message    string
	StackTrace string
	Misc       map[string]any
}

func (e MyError) Error() string { return e.Message }
func (e MyError) Unwrap() error { return e.Inner } // 让 errors.Is/As 能看穿这一层

// 顶层：沿包装链查找，而不是只断言最外层
var ierr IntermediateErr
if errors.As(err, &ierr) {
	msg = ierr.Error()
}
// Go 1.26+ 的泛型写法：
if ierr, ok := errors.AsType[IntermediateErr](err); ok {
	msg = ierr.Error()
}

// 结构化日志（Go 1.21+ log/slog），日志 ID 作为字段，方便检索
slog.Error("job failed", "logID", logID, "err", err, "stack", stack)

此外 Go 1.20 的 errors.Join 和 %w 多次使用，可以把多个错误合并成一个，适合「并发任务各自出错」的场景。

超时与取消

写并发代码时，超时和取消会频繁出现。超时对于构建「行为可以被理解」的系统至关重要；取消是对超时的一种自然反应，也可能有其他原因。

为什么要支持超时

系统饱和
如第 4 章「队列」所述，系统处理能力到达上限时，可能希望边缘的请求超时，而不是花很久去处理。一般在以下情况选择超时：请求超时后不太可能被重复发送； 没有资源存储请求（内存队列的内存、持久化队列的磁盘）；请求的需求或数据会过期。如果请求很可能被重复，系统会因为不断接受和超时请求而产生开销，开销超过容量就可能导致死亡螺旋。
数据过期
有时数据必须在某个时间窗口内处理，过了窗口就有更新的数据，或者不再需要处理。如果窗口事先已知，就给并发进程传一个 context.WithDeadline 或 WithTimeout 创建的 context； 如果事先未知，就让父亲在不再需要时用 context.WithCancel 取消它。
防止死锁
在大型系统（尤其分布式系统）里，有时很难理解数据怎样流动、会出现什么边界情况。给所有并发操作都加上超时以保证不会死锁，是合理甚至推荐的做法。 超时时长不必接近操作的实际耗时，只要短到死锁的系统能在可接受的时间内解锁。不过要注意：用超时避免死锁，可能把死锁变成活锁。但在大系统里， 下一次的时序不太可能和上次完全一样，所以宁可冒活锁的风险、有空再修，也比发生只能重启才能恢复的死锁好。这不是「正确构建系统」的方法，而是让系统能容忍你在开发测试时没覆盖到的时序错误；目标仍然应该是收敛到一个从不触发超时的无死锁系统。

并发进程为什么会被取消

超时

超时是一种隐式的取消。

用户干预

长时间运行的操作，通常要允许用户取消他们发起的操作。

父级取消

并发操作的任何一种「父亲」停止了，作为孩子的我们也会被取消。

复制请求

把请求发给多个处理者，第一个返回后取消其余的（本章后面详述）。

让代码可被抢占

「为什么取消」不难，难的是「怎样取消」：当并发进程被取消时，正在执行的算法和下游消费者会怎样？写可以随时被终止的并发代码，要考虑什么？ 首先是并发进程的可抢占性。假设下面的代码运行在自己的 goroutine 里： 

var value interface{}
select {
case <-done:
	return
case value = <-valueStream:
}

result := reallyLongCalculation(value) // 这一步没法被打断！

select {
case <-done:
	return
case resultStream <- result:
}

我们尽职地把读和写都和 done 放进了 select，但 reallyLongCalculation 看起来不可抢占，而且从名字看会跑很久。 如果在它执行时有人取消这个 goroutine，可能要过很久才会响应取消。试着让它可抢占： 

reallyLongCalculation := func(
	done <-chan interface{},
	value interface{},
) interface{} {
	intermediateResult := longCalculation(value)
	select {
	case <-done:
		return nil
	default:
	}

	return longCalculation(intermediateResult)
}

只解决了一半：只能在两次 longCalculation 之间被抢占。要彻底解决，longCalculation 本身也得可抢占：

reallyLongCalculation := func(
	done <-chan interface{},
	value interface{},
) interface{} {
	intermediateResult := longCalculation(done, value)
	return longCalculation(done, intermediateResult)
}
★ 可抢占性的两条原则
  1. 定义并发进程可被抢占的时间周期；
  2. 确保任何耗时超过这个周期的功能，本身也是可抢占的。简单的做法是把 goroutine 拆成更小的片段，让每个不可抢占的原子操作都能在这个周期内完成。

被取消时，共享状态怎么办？

还有一个潜在问题：如果 goroutine 修改了共享状态（数据库、文件、内存数据结构），被取消时怎么办？要回滚已做的中间工作吗？有多长时间做回滚？ 很难给出通用建议，但如果把对共享状态的修改限制在很小的范围内、并且容易回滚，通常就能很好地处理取消。尽可能在内存里构建中间结果，然后尽快修改状态。错误的做法：

✗ 写三次状态
result := add(1, 2, 3)
writeTallyToState(result)
result = add(result, 4, 5, 6)
writeTallyToState(result)
result = add(result, 7, 8, 9)
writeTallyToState(result)
✓ 在内存里算完，只写一次
result := add(1, 2, 3, 4, 5, 6, 7, 8, 9)
writeTallyToState(result)

左边如果在最后一次写之前被取消，就得设法回滚前两次写入；右边需要担心回滚的面积小得多。

重复消息

另一个要关心的问题是重复消息。假设管道有三个阶段：生成器、阶段 A、阶段 B。生成器通过记录距上次从 A 读取过了多久来监控 A， 如果 A 表现不佳就启动一个新实例 A2。这时 B 可能收到重复的消息：

避免重复消息的办法：

  • （推荐）让「孩子已经报告结果之后、父亲才发出取消」变得几乎不可能发生。这需要阶段之间的双向通信，下一节「心跳」会详细讲。
  • 接受第一个或最后一个结果：如果算法允许，或者并发进程是幂等的，可以允许下游收到重复消息，自己决定取第一个还是最后一个。
  • 向父 goroutine 请求许可：如图 5-4 右侧，用双向通信显式地请求发送许可。比心跳更安全，但更复杂，作者建议直接用心跳。
✓ 一开始就考虑超时和取消

设计并发进程时一定要考虑超时和取消。和软件工程的许多话题一样，一开始忽略、之后再加，就像蛋糕烤好了才想起来加鸡蛋。

心跳（Heartbeats）

心跳是并发进程向外界发出「我还活着」信号的方式，名字来自人体：心跳表示生命。心跳在 Go 之前就有了，在 Go 里依然有用。 它让我们能洞察系统的状态，还能让原本不确定的测试变得确定。本节讨论两种心跳：

  • 按时间间隔发出的心跳；
  • 在每个工作单元开始时发出的心跳。

按时间间隔的心跳

适用于「在等别的东西发生才能处理一个工作单元」的并发代码：你不知道工作什么时候来，goroutine 可能要闲坐一会儿。心跳是向监听者表明「一切正常，安静是预期中的」。 

doWork := func(
	done <-chan interface{},
	pulseInterval time.Duration,
) (<-chan interface{}, <-chan time.Time) {
	heartbeat := make(chan interface{}) // ① 发心跳的通道，返回给调用者
	results := make(chan time.Time)
	go func() {
		defer close(heartbeat)
		defer close(results)

		pulse := time.Tick(pulseInterval)       // ② 每隔 pulseInterval 跳一次
		workGen := time.Tick(2 * pulseInterval) // ③ 模拟工作到来，间隔比心跳长，好看到心跳

		sendPulse := func() {
			select {
			case heartbeat <- struct{}{}:
			default: // ④ 一定要有 default：可能没人在听心跳。结果很重要，心跳不重要
			}
		}
		sendResult := func(r time.Time) {
			for {
				select {
				case <-done:
					return
				case <-pulse: // ⑤ 和 done 一样：任何收发操作都要同时照顾心跳
					sendPulse()
				case results <- r:
					return
				}
			}
		}

		for {
			select {
			case <-done:
				return
			case <-pulse: // ⑤
				sendPulse()
			case r := <-workGen:
				sendResult(r)
			}
		}
	}()
	return heartbeat, results
}

因为等输入时、等发送结果时都可能要发出多次心跳，所有 select 都要放在 for 循环里。消费方这样用：

done := make(chan interface{})
time.AfterFunc(10*time.Second, func() { close(done) }) // ① 10 秒后关闭 done，给 goroutine 时间干点活

const timeout = 2 * time.Second                // ② 超时时间
heartbeat, results := doWork(done, timeout/2) // ③ 心跳间隔取超时的一半，多给一次机会，避免太敏感
for {
	select {
	case _, ok := <-heartbeat: // ④ 没有结果时，至少每 timeout/2 收到一次心跳；收不到说明 goroutine 本身出了问题
		if ok == false {
			return
		}
		fmt.Println("pulse")
	case r, ok := <-results: // ⑤ 正常接收结果
		if ok == false {
			return
		}
		fmt.Printf("results %v\n", r.Second())
	case <-time.After(timeout): // ⑥ 既没心跳也没结果，超时
		return

		defer close(workStream)

			case <-done:
				return
			case workStream <- rand.Intn(10):
			}
		}
	}()

}

有了心跳，不用超时也能安全地写测试。唯一的风险是某次迭代耗时过长。如果这很重要，可以用更安全的按间隔心跳做到万无一失： 

func DoWork(
	done <-chan interface{},
	pulseInterval time.Duration,
	nums ...int,
) (<-chan interface{}, <-chan int) {
	heartbeat := make(chan interface{}, 1)
	intStream := make(chan int)
	go func() {
		defer close(heartbeat)
		defer close(intStream)

		time.Sleep(2 * time.Second)

		pulse := time.Tick(pulseInterval)
	numLoop: // ② 用标签让内层循环能直接 continue 外层
		for _, n := range nums {
			for { // ① 两层循环：外层遍历数字，内层一直跑到这个数字成功发出为止
				select {
				case <-done:
					return
				case <-pulse:
					select {
					case heartbeat <- struct{}{}:
					default:
					}
				case intStream <- n:
					continue numLoop // ③ 发出成功，继续外层循环
				}
			}
		}
	}()
	return heartbeat, intStream
}

🆕 新版 Go：用 testing/synctest 写确定性的并发测试 Go 1.25+

		defer close(done)

				}

复制请求（Replicated Requests）

对某些应用来说，尽快拿到响应是第一要务：比如在处理用户的 HTTP 请求，或获取一块有多个副本的数据。这时可以做个取舍： 把请求复制给多个处理者（goroutine、进程或服务器），其中一个会比其他的快，立即返回它的结果。代价是要耗费资源维持多份处理者运行。 在内存里复制可能不贵，但如果要复制进程、服务器甚至数据中心，就很贵了。你要权衡成本是否值得。

下面在单个进程里用 10 个 goroutine 作为处理者，每个随机睡 1–5 秒模拟负载（书中正文写的是「纳秒」，但代码里实际是秒）：

doWork := func(
	done <-chan interface{},
	id int,
	wg *sync.WaitGroup,
	result chan<- int,
) {
	started := time.Now()
	defer wg.Done()

	// 模拟随机负载
	simulatedLoadTime := time.Duration(1+rand.Intn(5)) * time.Second
	select {
	case <-done:
	case <-time.After(simulatedLoadTime):
	}

	select {
	case <-done:
	case result <- id:
	}

	took := time.Since(started)
	// 显示如果没被取消，每个处理者本来要花多久
	if took < simulatedLoadTime {
		took = simulatedLoadTime
	}
	fmt.Printf("%v took %v\n", id, took)
}

done := make(chan interface{})
result := make(chan int)

var wg sync.WaitGroup
wg.Add(10)

for i := 0; i < 10; i++ { // ① 启动 10 个处理者
	go doWork(done, i, &wg, result)
}

close(done)               // ③ 取消其余的处理者，避免它们继续做无用功
wg.Wait()

⚠ 唯一的前提：处理者必须「各不相同」

所有处理者都要有同等的机会处理请求 —— 一个处理不了请求的处理者，不可能给你最快的结果；处理者用到的资源也要一起复制。 同一个问题的另一面是一致性：处理者太相似，出现「快的离群者」的机会就小。只应把请求复制给运行条件不同的处理者：不同的进程、机器、访问数据存储的路径，或者干脆是不同的数据存储。 虽然搭建和维护很贵，但如果速度是目标，这是很有价值的技术，还顺带提供了容错和扩展性。

func first(ctx context.Context, replicas []string) (Result, error) {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel() // 拿到第一个结果后，取消其余请求

	// 缓冲大小 = 副本数：落后者即使没人读也能发出结果并退出，不会泄漏
	results := make(chan Result, len(replicas))
	for _, addr := range replicas {
		go func() { results <- query(ctx, addr) }()
	}

	select {
	case r := <-results:
		return r, nil
	case <-ctx.Done():
		return Result{}, ctx.Err()
	}
}

同时发 N 份很浪费。业界常用的折中叫对冲请求（hedged requests），来自 Google 的论文 The Tail at Scale： 先发一份，如果在 P95 延迟内还没返回，再发第二份，取先到者。这样只多付出约 5% 的请求量，却能大幅削减长尾延迟。

限流（Rate Limiting）

用过服务 API 的人多半都碰到过限流：把对某种资源的访问次数限制在每单位时间某个有限数量内。资源可以是任何东西：API 连接、磁盘读写、网络包、错误。

为什么要限流？

  • 安全：防止一整类攻击。恶意用户如果能以他们资源允许的最快速度访问你的系统，就能做各种事：用日志或有效请求填满磁盘；如果日志轮转配置不当，甚至能做完坏事后再发足够多请求把痕迹挤出日志；暴力破解；DDoS……不限流，就很难保证系统安全。
  • 公平：分布式系统里，一个合法用户如果请求量太大或代码有 bug，会降低其他用户的体验，甚至引发死亡螺旋。用户心中的模型是「我的访问是沙箱化的，既不影响别人、也不受别人影响」，打破它会让系统显得设计不良。
  • 稳定：即使只有一个用户，系统在非常规负载下也可能出现意料之外的行为，在分布式系统中级联放大：丢包 → 分布式数据库失去法定人数、停止写入 → 现有请求失败 → …… 系统对自己发动 DDoS 也不是没听说过。
  • 商业：可以让用户在严格限制下免费试用（Google 云就是这么做的）；付费用户写出失控的 bug 时，限流也能保护他们免于天价账单。用户自己也可以在客户端设一个很低的限额，防止搬起石头砸自己的脚。
🔎 来自一线的故事

作者曾参与一个分布式系统：通过启动新进程水平扩展，每个进程打开数据库连接、读数据、计算。起初扩展得很好，但后来系统负载上升，数据库读取开始超时。 DBA 翻遍日志，最后发现：系统里什么都没限流，进程们互相践踏，磁盘争用飙到 100% 并一直维持，形成了一种「虐待式」的轮流超时重试循环，任务永远完不成。 后来给数据库连接数和每个连接每秒读取的字节数加了限制，问题消失了。客户要等更久，但任务能完成，团队也能按部就班地做容量规划。

限流让你能推理系统的性能和稳定性：它防止系统跑出你已经研究过的边界。如果需要扩大边界，可以在大量测试和咖啡之后，有控制地扩大。

令牌桶算法

大多数限流用的是令牌桶（token bucket）算法，容易理解，也相对容易实现：

  • 要使用资源，必须有一个访问令牌，没有令牌请求就被拒绝（或排队等待）；
  • 令牌放在一个桶里，桶的深度 d 表示最多能装多少个令牌；
  • 每次访问资源，从桶里拿走一个令牌；
  • 令牌以速率 r 补充回桶里（可以是每纳秒一个，也可以是每分钟一个）。这就是我们通常说的「速率限制」。

// Limit 定义某类事件的最大频率，表示为每秒事件数。0 表示不允许任何事件。
type Limit float64

// NewLimiter 返回一个允许速率 r、最多突发 b 个令牌的限流器。
func NewLimiter(r Limit, b int) *Limiter

// Every 把「事件之间的最小间隔」转换成 Limit。
func Every(interval time.Duration) Limit

// Wait 是 WaitN(ctx, 1) 的简写。
func (lim *Limiter) Wait(ctx context.Context) error

// WaitN 阻塞直到允许 n 个事件发生。如果 n 超过突发上限、ctx 被取消、
// 或预计等待时间超过 ctx 的截止时间，返回错误。
func (lim *Limiter) WaitN(ctx context.Context, n int) (err error)

func Per(eventCount int, duration time.Duration) rate.Limit {
	return rate.Every(duration / time.Duration(eventCount))
}

func Open() *APIConnection {
	return &APIConnection{
		rateLimiter: rate.NewLimiter(rate.Limit(1), 1), // ① 所有 API 调用合计每秒 1 次
	}
}

多级限流

生产环境往往需要多层限制：细粒度的每秒限制，加上粗粒度的每分钟、每小时、每天限制。有时一个限流器就能做到，但并非总能做到；而且把「每单位时间的限制」揉进一层，会丢失很多关于意图的信息。 作者更喜欢把限流器分开，再组合成一个统一管理的限流器： 

type RateLimiter interface { // ① 定义接口，让 MultiLimiter 可以递归地包含其他 MultiLimiter
	Wait(context.Context) error
	Limit() rate.Limit
}

func MultiLimiter(limiters ...RateLimiter) *multiLimiter {
	byLimit := func(i, j int) bool {
		return limiters[i].Limit() < limiters[j].Limit()
	}
	sort.Slice(limiters, byLimit) // ② 优化：按限制从严到松排序
	return &multiLimiter{limiters: limiters}
}

type multiLimiter struct {
	limiters []RateLimiter
}

func (l *multiLimiter) Wait(ctx context.Context) error {
	for _, l := range l.limiters {
		if err := l.Wait(ctx); err != nil {
			return err
		}
	}
	return nil
}

func (l *multiLimiter) Limit() rate.Limit {
	return l.limiters[0].Limit() // ③ 因为排过序，第一个就是最严格的
}

Wait 依次等待每个子限流器。这些调用可能阻塞也可能不阻塞，但必须通知每个限流器以便扣减令牌。依次等待的结果是恰好等待最长的那段时间： 前面短的等待在阻塞时，后面的桶也在补充令牌，所以轮到最长的那个时，只需等剩余的时间，之后的等待会立即返回。 

func Open() *APIConnection {
	secondLimit := rate.NewLimiter(Per(2, time.Second), 1)   // ① 每秒 2 次，没有突发
	minuteLimit := rate.NewLimiter(Per(10, time.Minute), 10) // ② 每分钟 10 次，突发 10 个作为初始额度
	return &APIConnection{
		rateLimiter: MultiLimiter(secondLimit, minuteLimit), // ③ 组合成总限流器
	}
}

func Open() *APIConnection {
	return &APIConnection{
		apiLimit: MultiLimiter( // ① API 调用：每秒和每分钟都有限制
			rate.NewLimiter(Per(2, time.Second), 2),
			rate.NewLimiter(Per(10, time.Minute), 10),
		),
		diskLimit: MultiLimiter( // ② 磁盘：每秒 1 次
			rate.NewLimiter(rate.Limit(1), 1),
		),
		networkLimit: MultiLimiter( // ③ 网络：每秒 3 次
			rate.NewLimiter(Per(3, time.Second), 3),
		),
	}
}

type APIConnection struct {
	networkLimit,
	diskLimit,
	apiLimit RateLimiter
}

func (a *APIConnection) ReadFile(ctx context.Context) error {
	err := MultiLimiter(a.apiLimit, a.diskLimit).Wait(ctx) // ④ 读文件：API 限制 + 磁盘限制
	if err != nil {
		return err
	}
	// 假装这里在干活
	return nil
}

func (a *APIConnection) ResolveAddress(ctx context.Context) error {
	err := MultiLimiter(a.apiLimit, a.networkLimit).Wait(ctx) // ⑤ 解析域名：API 限制 + 网络限制
	if err != nil {
		return err
	}
	// 假装这里在干活
	return nil
}

不必为每个调用画时间表 —— 关键是我们能把逻辑上的限流器组合成对每个调用都合理的分组，APIClient 会做正确的事。 rate.Limiter 还有其他技巧（优化与其他用例），这里只用了「等待直到拿到下一个令牌」这一种。

🆕 新版 Go：限流的现代补充
  • golang.org/x/time/rate 依然是 Go 生态最常用的令牌桶实现。除 Wait 外，Allow() 用于「拿不到就立刻拒绝」（比如 HTTP 中间件返回 429），Reserve() 可以先预订再决定，SetLimit/SetBurst 可以运行时调整。
  • Go 1.21+ sort.Slice(limiters, byLimit) 可以写成类型安全的 slices.SortFunc(limiters, func(a, b RateLimiter) int { return cmp.Compare(a.Limit(), b.Limit()) })。
  • 书中的 multiLimiter.Wait 有个细节：如果前一个限流器已经扣了令牌、后一个因 ctx 取消而失败，前面扣掉的令牌不会退还。对精确计费的场景，需要用 Reserve 再 Cancel 来实现。
  • 多实例部署时，进程内限流只能限制单个实例；全局限流通常放在网关或借助 Redis 等共享存储实现。

自愈的 goroutine

在守护进程这种长期运行的程序里，常常有一组长期存活的 goroutine。它们通常阻塞着，等数据以某种方式到来，然后醒来干活、再把数据传下去。 有时 goroutine 依赖的资源你控制不好：也许要从某个 Web 服务拉数据，或在监控一个临时文件。goroutine 很容易陷入一种没有外力帮助就无法恢复的坏状态。 如果按关注点分离，「干活的 goroutine 知道怎样从坏状态治愈自己」本就不该是它的职责。 在长期运行的进程里，建立一种机制来确保 goroutine 保持健康、不健康时重启它，会很有用。我们把重启 goroutine 的过程称为治愈（healing）。

治愈要用心跳来检查被监控 goroutine 的活性。心跳的类型取决于你要监控什么：如果 goroutine 可能活锁，心跳里要包含能证明「它不仅活着、还在做有用的事」的信息。 简单起见，这里只考虑活着还是死了。我们把监控健康的逻辑叫管家（steward），被监控的 goroutine 叫被监护者（ward）。 管家还负责在被监护者不健康时重启它，所以需要一个能启动它的函数：

🔎 熟悉 Erlang 的读者

会认出这个概念：Erlang 的 supervisor（监督者）做的就是类似的事。

type startGoroutineFn func(
	done <-chan interface{},
	pulseInterval time.Duration,
) (heartbeat <-chan interface{}) // ① 可被监控、可被重启的 goroutine 的签名：熟悉的 done、心跳间隔、心跳通道

newSteward := func(
	timeout time.Duration,
	startGoroutine startGoroutineFn,
) startGoroutineFn { // ② 管家接收被监护者的超时时间和启动函数；有趣的是，它自己也返回 startGoroutineFn —— 管家本身也可以被监控
	return func(
		done <-chan interface{},
		pulseInterval time.Duration,
	) <-chan interface{} {
		heartbeat := make(chan interface{})
		go func() {
			defer close(heartbeat)

			var wardDone chan interface{}
			var wardHeartbeat <-chan interface{}
			startWard := func() { // ③ 封装「以一致的方式启动被监护者」
				wardDone = make(chan interface{})                             // ④ 每次启动都新建一个 done，以便需要时单独叫停这个被监护者
				wardHeartbeat = startGoroutine(or(wardDone, done), timeout/2) // ⑤ 管家被停止，或管家想停止被监护者，被监护者都要停 → 用 or 组合两个 done
			}
			startWard()
			pulse := time.Tick(pulseInterval)

		monitorLoop:
			for {
				timeoutSignal := time.After(timeout)

				for { // ⑥ 内层循环：保证管家自己也能发出心跳
					select {
					case <-pulse:
						select {
						case heartbeat <- struct{}{}:
						default:
						}
					case <-wardHeartbeat: // ⑦ 收到被监护者的心跳，重新开始一轮监控（重置超时）
						continue monitorLoop
					case <-timeoutSignal: // ⑧ 超时没收到心跳：叫停被监护者，启动一个新的
						log.Println("steward: ward unhealthy; restarting")
						close(wardDone)
						startWard()
						continue monitorLoop
					case <-done:
						return
					}
				}
			}
		}()

		return heartbeat
	}
}

doWorkFn := func(
	done <-chan interface{},
	intList ...int,
) (startGoroutineFn, <-chan interface{}) { // ① 接收被监护者要闭包引用的值，返回被监护者用来回传数据的通道
	intChanStream := make(chan (<-chan interface{})) // ② 「通道的通道」，bridge 模式的一部分
	intStream := bridge(done, intChanStream)
	doWork := func(
		done <-chan interface{},
		pulseInterval time.Duration,
	) <-chan interface{} { // ③ 这个闭包会被管家启动和监控
		intStream := make(chan interface{}) // ④ 这一次启动所用的新通道
		heartbeat := make(chan interface{})
		go func() {
			defer close(intStream)
			select {
			case intChanStream <- intStream: // ⑤ 告诉 bridge：之后从这个新通道读
			case <-done:
				return
			}

			pulse := time.Tick(pulseInterval)

			for {
			valueLoop:
				for _, intVal := range intList {
					if intVal < 0 {
						log.Printf("negative value: %v\n", intVal) // ⑥ 模拟不健康：遇到负数就记错误并退出
						return
					}

					for {
						select {
						case <-pulse:
							select {
							case heartbeat <- struct{}{}:
							default:
							}
						case intStream <- intVal:
							continue valueLoop
						case <-done:
							return
						}
					}
				}
			}
		}()
		return heartbeat
	}
	return doWork, intStream
}

因为可能启动多个被监护者实例，这里用了第 4 章的 bridge，为 doWork 的消费者呈现一个不间断的通道。组合模式就能让被监护者任意复杂：

原来：每次重启从头遍历
valueLoop:
for _, intVal := range intList {
	// ...
}
改为：消费一个就从列表里移除
valueLoop:
for {
	intVal := intList[0]
	intList = intList[1:]
	// ...
}

这样重启之间就能保存进度，不过我们会一直卡在那个无效的负数上，被监护者会不停失败。用这个模式，能帮助你的长期 goroutine 保持健康运行。

🆕 新版 Go：今天的「监督」怎么做
  • 用 context.Context 代替 done 通道和 or：wardCtx, cancelWard := context.WithCancel(ctx)，父 ctx 取消时被监护者自动取消，管家想重启时调用 cancelWard()。
  • 社区有成熟的 Erlang 风格监督树库，如 github.com/thejerf/suture，处理了退避重启、失败阈值、日志等细节。
  • 在容器编排时代，很多「自愈」交给了进程级别：Kubernetes 的 liveness 探针就是「心跳 + 重启」的进程版。进程内的监督仍然适合重启单个子任务、而不想整个进程重启的场景。
  • 如果被监护者可能 panic，管家里还要用 recover 捕获，否则一个 goroutine 的 panic 会让整个进程崩溃。

本章小结

主题核心做法
错误传播错误要包含「发生了什么、何时何地、友好消息、日志 ID」；在模块边界包装；未包装的原始错误 = bug
超时与取消为饱和、过期数据、防死锁而超时；让长计算分段可抢占；共享状态尽量最后一次性修改
心跳按间隔的心跳监控健康；按工作单元的心跳写确定性测试（今天还可以用 synctest）
复制请求同一请求发给多个「不同条件」的处理者，取最快的，取消其余
限流令牌桶：d 控制突发、r 控制速率；按时间和资源维度组合多个限流器
自愈steward 用心跳 + 超时监控 ward，不健康就叫停并重启；用 bridge 给消费者一个不间断的流
